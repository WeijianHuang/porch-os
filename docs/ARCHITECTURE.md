# 架构原则

> 状态：早期工程阶段。数据库已定为 **PostgreSQL 18.7**（[ADR-0001](decisions/0001-postgresql-18.md)），后端技术栈已定为 **Go + SQL 优先**（[ADR-0002](decisions/0002-go-backend-stack.md)），数据隔离模型已由 [ADR-0003](decisions/0003-shop-level-isolation.md) 锁定为**仅门店层**，业务范围基线已由 [ADR-0004](decisions/0004-scope-baseline.md) 锁定为**单币种 CNY / 统一 UTC+8 / 暂不归档 / 不打印 / 不离线**，门店组概念已由 [ADR-0005](decisions/0005-no-shop-groups.md) 取消（跨店改用显式门店集合），用户可拥有多间门店与「当前门店」切换协议已由 [ADR-0006](decisions/0006-user-shops-and-current-shop.md) 定义；**剩余开放问题已由 [ADR-0007](decisions/0007-remaining-open-questions.md) 全部关闭**：R1 不接外部服务、前端框架归属 `porch-console`、支持编排平台且暂不读写分离、不做跨店自动清分、审计日志保留 30 天可配并定时删除。隔离模型见第 2.0 节，数据层落地见第 2.1 节，技术栈落地见第 8 节。前端框架由 `porch-console` 独立决策（NQ-14 已决：以既有内部前端工程实践为依据，工程名称不写入公开仓库）。**NQ-01–16 全部关闭、DP-01–07 全部接受，前期系统架构详细设计已冻结**（[ADR-0008](decisions/0008-design-freeze-and-nq-resolutions.md)：Docker 2+2 + Go `cmd/job` + 数据库共享、R1 范围与验收标准），见 [`design/00-overview.md`](design/00-overview.md)。后续模块级选型继续以 ADR 记录并回写本文。

## 1. 术语表

| 术语 | 含义 | 备注 |
|---|---|---|
| `Shop` | 单店，最小经营与核算单位 | 所有业务数据的归属维度，也是**唯一**隔离维度 |
| 门店组 / 店群 | **不使用**（[ADR-0005](decisions/0005-no-shop-groups.md)） | 不设 `ShopGroup`、分组表、父子门店或标签分组；跨店用显式门店 ID 集合表达 |
| `shop_id` | 门店维度字段 | 业务表必带；不存在更上层的隔离键 |
| 跨店视角 | 跨店查看与汇总的能力 | 是权限范围，不是独立的数据副本，也不是组织层 |
| 可见门店集合 | 一个用户被授权管理的 N 家门店 | 从 `user_shops` 每次请求实时推导；关系是多对多（一店也可有多个账号），见 [ADR-0006](decisions/0006-user-shops-and-current-shop.md) |
| 当前门店 | 页面此刻正在看的那一家店 | 请求期上下文，客户端持有、服务端求交校验；不落库、不进 JWT、不是授权来源，可在页面切换 |

**明确不用**：`tenant_id` / `org_id` / `company_id` / 租户 / 组织 / 集团（本项目只有一个经营主体，不引入上层隔离维度，见 ADR-0003）、`ShopGroup` / 门店组 / 店群 / 父子门店 / 门店标签分组（取消分组实体，见 [ADR-0005](decisions/0005-no-shop-groups.md)）、`users.shop_id` / `shops.owner_user_id` 单外键、`current_shop` 表 / 用户偏好表 / 服务端切换端点（把用户锁死单店或引入服务端状态，见 ADR-0006）、`Chain` / `Franchise`（暗示加盟体系，对小门店过重）、`Outlet` / `Branch`（前者有折扣店歧义，后者偏总部-分支制）。

## 2. 多店数据隔离（最高优先级约束）

### 2.0 隔离模型（唯一权威，见 ADR-0003）

**数据隔离只有一层：`shop_id`。** 所有门店属于同一个经营主体，单库、单 schema、一套用户体系；不存在 tenant / org / company / 集团等上层维度，也不把它们作为数据归属、授权边界或查询条件。

| 规则 | 说明 |
|---|---|
| 唯一隔离键 | 所有业务表带 `shop_id`；复合索引与唯一约束以它为前导列 |
| 禁止 | `tenant_id` / `org_id` / `company_id` 列、schema-per-shop、按会话变量做 RLS 过滤、任何 tenant scope 中间件 |
| 门店组 | **不存在**（[ADR-0005](decisions/0005-no-shop-groups.md)）：不设分组实体、分组表、分组端点与按组授权；跨店范围由「可见门店集合 + 显式 `shop_ids`」给出，一条业务记录始终只属于一个 `shop_id` |
| 全局实体 | 会员档案、商品目录等不带隔离维度、全局唯一；其余额变动、消费流水、库存、单据必须带 `shop_id` |
| 跨店查询 | 在「当前用户可见门店集合」上聚合，显式声明并单独授权；不产生数据副本 |
| 授权 | 「用户 ↔ 可见门店集合」直接关系（一个用户可关联多间门店，关系是多对多），不经过任何上层实体，不缓存判定结果 |
| 当前门店 | 请求期上下文：客户端显式携带、服务端与可见集合求交；不落库、不进 JWT、无服务端切换端点，切换不改变授权与数据归属（[ADR-0006](decisions/0006-user-shops-and-current-shop.md)） |
| 可见性 | 隔离条件必须显式出现在 SQL 与调用链中，便于评审与 `EXPLAIN` 检查 |

漏加一次门店条件不会报错，只会静默返回别家店的数据——这也是不引入第二层维度的核心原因：错误组合会翻倍。完整决策、备选方案与复审条件见 [ADR-0003](decisions/0003-shop-level-isolation.md)。

1. 所有业务表带 `shop_id`，并在服务层入口统一注入当前可访问门店范围。
2. **默认查询必须带门店条件**；跨店查询必须显式声明，且单独做授权校验。
3. 门店参数绝不信任客户端传入的裸值；以认证主体 + 角色推导出的可见门店集合为准。
4. 汇总类查询按门店维度聚合，避免把不同门店数据混进同一结果行。
5. 单号、流水号等唯一性约束必须考虑「同一门店内」还是「全局」，不能只靠应用层拼接生成。

### 2.1 数据库层落地（PostgreSQL 18.7）

数据库与后端技术栈均已确定；以下是必须先固定的 schema 约定，不随框架选型变化：

| 主题 | 约定 |
|---|---|
| 门店维度 | 业务表一律带 `shop_id`，它是唯一隔离维度；复合索引与唯一约束以 `shop_id` 为前导列 |
| 唯一性范围 | 单号、流水号的唯一约束必须写明是「店内唯一」还是「全局唯一」，不能靠应用层拼接；不存在「租户内唯一」 |
| 金额 | `numeric(p, s)`，禁止浮点类型；应用层用定点十进制；**单币种 CNY，不设 `currency` 列、不存汇率** |
| 时间 | `timestamptz` 统一 UTC 存储、ISO 8601 UTC 传输；**展示、业务日与单号日期统一 `Asia/Shanghai`（UTC+8）**，不设门店级时区 |
| 业务日 | `(occurred_at AT TIME ZONE 'Asia/Shanghai')::date` + 门店营业日切点偏移；日报、班次、汇总、导出共用这一口径 |
| 数据保留 | **业务数据暂不归档**：单据、支付与流水在线全量保留，不设保留窗口、不分区；运行期数据（幂等键、已投递事件、导出临时文件）照常清理，**`audit_logs` 默认保留 30 天、可配、由 worker 定时删除**（ADR-0007）；业务单据与流水不参与任何定期删除 |
| 主键 | `bigint generated always as identity`；对外单号与内部主键分开 |
| 变更 | 只走版本化的可回滚迁移文件（goose 执行、atlas 查漂移），禁止手工改库 |
| 计算口径 | 不把业务逻辑放进数据库视图；复杂口径写在受版本控制的 SQL 中 |

版本选择、代价与复审条件见 [ADR-0001](decisions/0001-postgresql-18.md)；本地实例见 [`LOCAL-DEV.md`](LOCAL-DEV.md)。

## 3. 分层与依赖方向

```
接口层（HTTP 适配）  →  应用/服务层  →  领域层  →  数据访问层
```

- 接口层只做参数解析、调用服务、格式化响应，**不写业务规则**。
- 服务层承载业务规则与编排，**不依赖请求/响应对象**，可脱离协议单测。
- 领域层放纯函数与值对象（金额计算、状态机、折叠/聚合逻辑），不触碰数据库。
- 数据访问层负责查询与外部调用，返回场景专用的扁平结构，不引入实体关联图与隐式加载。
- 依赖单向向下，通过依赖注入解耦；禁止反向依赖与跨层直连。

## 4. 工程稳健性

| 主题 | 约定 |
|---|---|
| 配置 | 全部来自环境变量，启动时集中校验、缺失即快速失败；密钥只存在本地环境 |
| 错误 | 类型化错误体系 + 全局处理中间件；客户端只看到规范化错误结构，绝不返回堆栈或内部细节 |
| 日志 | 结构化 JSON，贯穿 request id；不记录密码、令牌与隐私数据 |
| 输入校验 | 所有外部输入在边界处校验，服务层不假设数据已合法 |
| 写入 | 多步写入放事务；并发更新用乐观锁或行锁，冲突返回显式错误 |
| 幂等 | 所有会产生业务副作用的写操作提供幂等键；回调与重试不重复记账 |
| 迁移 | schema 变更一律走可回滚迁移文件，禁止手工改库 |
| 缓存 | 一律设置 TTL，写后失效；不缓存跨店权限判定结果 |
| 后台任务 | 独立进程、幂等、失败重试并进入死信队列；不在请求处理器里跑长任务 |
| 报表导出 | 流式写出，禁止把整个文件读进内存后再返回 |
| 超时 | 所有外部调用与数据库查询接受 context，客户端断开后服务端计算必须终止 |
| 在线与外设 | **不支持离线收银与打印**（[ADR-0004](decisions/0004-scope-baseline.md)）：不建本地队列、补传、冲突合并、打印任务或设备适配；文件导出保留 |

## 5. 接口与前端集成

- 接口风格为 **REST + OpenAPI**，契约由注释生成并保持可 diff；契约变更需同步 `porch-console`。
- 不提供门店组 / 店群端点与分组筛选参数（[ADR-0005](decisions/0005-no-shop-groups.md)）；跨店汇总只用可见门店集合 + 显式门店 ID。
- **门店上下文与切换**（[ADR-0006](decisions/0006-user-shops-and-current-shop.md)）：登录返回可见门店集合与默认门店，`/me/shops` 是切换器唯一数据源；单店请求必须显式带 `X-Shop-Id`，缺头 `400`、越权 `403`；**不提供服务端切换端点**，切换是纯客户端行为（改带头 + 失效缓存 + 重取权限），且不得把当前门店当作权限依据。
- 金额（CNY）与时区（UTC+8）由 [ADR-0004](decisions/0004-scope-baseline.md) 全局固定：接口不带币种字段、不接受时区参数；文件导出可用，打印端点不存在。
- 错误响应统一结构（错误码、可读消息、request id），便于前端映射文案。
- 列表接口统一分页参数与返回形状；排序字段走白名单。
- CORS 使用显式来源白名单，生产禁用通配符。

## 6. 认证与授权

- 认证采用 **JWT 短时效访问令牌 + 服务端存储的刷新令牌**；密码哈希用 bcrypt，令牌不进 URL 查询参数。
- 授权 = 角色权限（能做什么） + 门店维度（能对哪些店做），两者缺一不可。
- 「用户 ↔ 可见门店集合」是直接关系，不经过租户 / 组织等上层实体；权限判定结果不因缓存而与实时授权不一致，刷新后必须立即生效。一个用户可关联多间门店，关系实现为 `user_shops` 多对多（一店也可有多个账号），不是 `users.shop_id` 外键（ADR-0006）。
- **当前门店不是授权来源**：客户端持有并在每次单店请求显式携带，服务端用 `user_shops` 实时求交；不落库、不进 JWT、无服务端切换端点，切换不触发授权重算（ADR-0006）。

## 7. 实时能力与上线清单

- 实时采用 **WebSocket**，长连接需含心跳与断线重连；服务端推送携带门店维度，不跨店广播。
- 上线前：健康检查 `/health` 与就绪检查 `/ready`、优雅停机、安全响应头、限流、HTTPS、结构化日志与指标、超时与连接池上限。

## 8. 后端技术栈落地（ADR-0002）

| 层 | 落地方式 |
|---|---|
| 接口 | Gin v1.10 路由分组 + 中间件注入 request id 与门店范围；OpenAPI 由 `swaggo/swag` 生成 |
| 隔离 | 中间件注入的是 **shop scope**（可见门店集合），不是 tenant scope；不引入租户插件或 RLS |
| 应用 | 自建 Unit of Work，`*sql.Tx` 挂在 context 上，事务边界显式可见 |
| 领域 | 纯函数与值对象；一对多折叠逻辑放在 `internal/domain/`，可脱离 DB 单测 |
| 数据访问 | sqlc 管静态 SQL、squirrel 管动态筛选（**必须 `PlaceholderFormat(squirrel.Dollar)`**）、pgx/v5 管连接与类型映射 |
| 金额 | shopspring/decimal ↔ PG `numeric`，禁止 `float64`；单币种 CNY，无币种字段与汇率 |
| 缓存 | Redis（跨实例）+ ristretto（进程内），带 TTL、写后失效 |
| 可观测性 | slog JSON 日志 + Prometheus 指标 + OpenTelemetry 链路 |
| 测试 | 领域逻辑纯函数单测；集成测试用 testcontainers-go 起真实 PG，不 mock 服务层 |
| 部署 | 多阶段构建 → `distroless/static`；`api` / `worker` 无状态、支持编排平台水平扩缩；**单主库读写，暂不读写分离 / 只读副本**；迁移由独立一次性任务执行、定时任务靠数据库锁防重、连接池预算 80 ≤ 100（ADR-0007 / ADR-0008）。**本期落地 Docker 2+2 + Go `cmd/job` + 数据库共享，见 `design/07`**；本地 Compose 仅用于开发 |

**代码评审阻断项**：① 不建实体关联图，结构体之间只持 ID；② 一条查询返回一个场景专用扁平 DTO；③ 不使用数据库视图承载计算口径；④ 动态查询必须用 `$1` 占位符且排序字段走白名单；⑤ 金额禁用浮点；⑥ 写操作必须带幂等键，单号唯一性靠数据库约束并写明范围；⑦ 报表导出流式写出；⑧ 跨店权限判定不缓存；⑨ 集成测试用真实 PG 容器；⑩ **不引入 `tenant_id` / `org_id` / `company_id` 或任何上层隔离维度**（ADR-0003），也不引入门店组 / 分组实体（ADR-0005）；⑪ **不把当前门店做成服务端状态**：禁止 `users.shop_id` / `shops.owner_user_id` 单外键、`current_shop` 表、切换端点或把当前门店写进 JWT，单店请求缺 `X-Shop-Id` 必须报 400（ADR-0006）；⑫ **不引入 R1 范围外的外部 SDK、只读副本 / 读写分离、内部往来账或自动清分**，不在进程启动时跑迁移，审计记录只允许 worker 清理任务删除（ADR-0007）。

R0 引导骨架仅用标准库提供 `/health`，零外部依赖，作为 CI 基线保留。R1 已落地首批依赖：Gin v1.10、pgx/v5、goose、squirrel、golang-jwt/v5、bcrypt、shopspring/decimal。上表中的 sqlc、Redis / ristretto、Prometheus / OpenTelemetry、swaggo、testcontainers-go 等为**已选定但尚未引入 `go.mod`** 的目标，按模块逐步引入，不一次性堆入。完整理由、备选方案与不选什么见 [ADR-0002](decisions/0002-go-backend-stack.md)。
