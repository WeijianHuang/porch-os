# ADR-0001: 数据库选用 PostgreSQL 18.7

- 状态：已接受（2026-11-15）
- 决策问题：Porch OS 的第一个技术栈决策——多店经营系统用哪个数据库、哪个大版本
- 影响范围：`porch-os` 的数据层、迁移方式与本地开发环境；`porch-console` 不受直接影响（前端不直连数据库）

## 背景

- 系统面向通用小微门店、支持多店：业务表天然带 `shop_id` 维度，既有单店明细，也有跨店汇总与按店对比。
- 报表场景依赖条件聚合、CTE、窗口函数与分区扫描；金额计算必须精确十进制。
- 本决策只锁定数据库，不预设其余选型；后端技术栈随后由 [ADR-0002](0002-go-backend-stack.md) 确定，前端框架由 `porch-console` 独立决策。
- 需要一个本地可复现、生命周期足够长的版本，避免刚起步就面临 EOL。

## 备选方案

| 方案 | 当前小版本 | 首次发布 | EOL | 优点 | 代价 |
|---|---|---|---|---|---|
| A. PostgreSQL 18 | 18.7 | 2025-09-25 | 2030-11-14 | 支持周期最长；内置 `uuidv7()`；异步 I/O 改善大表扫描；B-tree skip scan、虚拟生成列、`RETURNING old/new` | 最新大版本，个别第三方代码生成 / 迁移工具对 18 特有语法的解析可能滞后 |
| B. PostgreSQL 17 | 17.12 | 2024-09-26 | 2029-11-08 | 工具链兼容最保守，云厂商覆盖广 | 少一年支持；无内置 `uuidv7()` 与异步 I/O |
| C. PostgreSQL 16 | 16.16 | 2023-09-14 | 2028-11-09 | 生态最成熟 | 支持期最短，很快进入升级窗口 |
| D. MySQL 8.x | — | — | — | 普及度高 | 与条件聚合、CTE、`jsonb`、扩展生态等诉求不匹配，不采用 |

> 版本与 EOL 取自 PostgreSQL 官方 Versioning Policy（2026-11-15 核对）。PG 14 已于 2026-11-12 EOL，不列入候选。PG 18 特性依据官方 18.0 Release Notes。

## 决策

采用 **PostgreSQL 18.7**。本地与 CI 固定到该小版本（或等价 digest）；生产保持同一大版本，只升补丁版本。

配套约定：

- 金额一律 `numeric(p, s)`，禁止浮点；单币种 CNY，不设 `currency` 列。时间用 `timestamptz`，统一以 UTC 存储、ISO 8601 UTC 传输，**展示、业务日与单号日期统一按 `Asia/Shanghai`（UTC+8）**，不设门店级时区——口径见 [ADR-0004](0004-scope-baseline.md)。
- 主键用 `bigint generated always as identity`；对外单号另设唯一约束，且必须明确唯一范围是「店内唯一」还是「全局唯一」。
- 所有业务表带 `shop_id`；高频查询的复合索引以 `shop_id` 为前导列，唯一约束同理。
- schema 变更只走版本化的可回滚迁移文件，禁止手工改库；迁移工具、连接池与查询构建方式见 [ADR-0002](0002-go-backend-stack.md)。
- 业务逻辑不放在数据库视图里：视图一旦游离于版本管理，计算口径就失去唯一来源；复杂口径写在受版本控制的 SQL 中。
- 本地实例用官方 `postgres:18.7` 镜像 + Docker Compose 启动，见 [`../LOCAL-DEV.md`](../LOCAL-DEV.md)。

## 理由

1. **生命周期**：18.x 支持到 2030-11，五年窗口覆盖项目从 0 到 1 的全过程，避免短期内被迫跨大版本升级。
2. **贴合多店报表**：条件聚合 / CTE / 窗口函数是跨店汇总的主力写法；18 的异步 I/O 对顺序扫描、位图堆扫描与 vacuum 有实际收益，B-tree skip scan 也让多列索引在更多查询下可用。
3. **单号与幂等**：`uuidv7()` 提供时间有序 UUID，可作为跨店单号与幂等键的候选，降低应用层自增序列的并发风险。
4. **不锁定其余选型**：PG 与语言、框架、部署方式解耦，后续无论选哪种后端栈都不冲突。
5. **可复现**：官方镜像按小版本 pin，本地 / CI / 生产大版本一致，避免方言与行为差异。

## 后果与限制

- 若生产目标改为尚未提供 18 的云托管数据库，需**同步降级到 17.12**，并更新本 ADR、Compose 与所有版本引用；不允许本地 18 / 生产 17 长期混用。降级时还需复查 `uuidv7()` 的应用层替代方案（见 ADR-0002）。
- 第三方工具若不能解析 18 特有语法，优先只用标准 SQL 与通用特性；本项目也不打算依赖数据库专有对象。
- 数据库不启用任何租户层语义：门店隔离靠 `shop_id` + 服务层授权，不存在 `tenant_id` 或更上层的隔离维度；隔离模型的唯一权威见 [ADR-0003](0003-shop-level-isolation.md)。
- 官方容器镜像 18+ 的数据目录改为 `/var/lib/postgresql/18/docker`、卷挂载点改为 `/var/lib/postgresql`；沿用旧版镜像的 `/var/lib/postgresql/data` 会启动失败，本地与部署脚本必须按新约定写。
- 驱动、连接池、迁移工具与事务边界已由 [ADR-0002](0002-go-backend-stack.md) 确定；本 ADR 的「配套约定」与之保持一致，不单独重复。

## 复审条件

- PostgreSQL 19 发布且工具链跟进后评估升级；
- 生产部署目标确定为某云厂商、且该厂商最高只支持 17 时；
- 出现必须依赖某扩展而 18 尚不支持的情况。
