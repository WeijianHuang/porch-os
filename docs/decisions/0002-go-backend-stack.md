# ADR-0002: 后端技术栈选用 Go + SQL 优先

- 状态：已接受（2026-11-15）
- 决策问题：在 ADR-0001 已锁定 PostgreSQL 18.7 之后，后端用什么语言、框架与数据访问方式实现
- 影响范围：`porch-os` 全部后端源码、CI、迁移与测试方式；`porch-console` 的接口风格受本决策影响，前端框架不在本决策范围

## 背景

Porch OS 是通用多店经营系统，负载特征决定选型，而不是反过来：

1. **金额与数量必须精确**：价格、折扣、余额、库存数量都不允许二进制浮点误差。
2. **跨店汇总是主要读负载**：报表依赖条件聚合、CTE、窗口函数，且筛选条件可自由组合。
3. **门店隔离是第一约束**：所有业务表带 `shop_id`，默认查询必须显式带门店条件；任何隐式加载都可能绕过这条约束且静默返回别家店的数据。
4. **写操作跨多张表**：开单、收银、库存扣减要求显式事务边界与乐观锁 / 行锁，不能依赖隐式刷新。
5. **报表导出不能全量进内存**：需流式写出，否则大区间导出会随数据量线性吃满内存。
6. **权限变更必须立即生效**：跨店权限判定结果不允许缓存。
7. **没有可依赖的既有测试网**：集成测试必须能起真实数据库容器，领域逻辑必须能脱离数据库单测。
8. **这是单库多店，只有一层隔离**：隔离靠 `shop_id` + 服务层授权，不需要租户插件、上层维度或行级安全策略，见 [ADR-0003](0003-shop-level-isolation.md)。

数据库已由 [ADR-0001](0001-postgresql-18.md) 锁定 PostgreSQL 18.7。本 ADR 只决定数据库之上的实现栈。

## 备选方案

| 方案 | 描述 | 代价 |
|---|---|---|
| A. 全功能 ORM + 实体关联图 | 结构体嵌套关联实体，靠隐式加载取数据 | 关联加载深度随调用方漂移，N+1 难用 `EXPLAIN` 定位；报表退化为字符串拼接；动态筛选变成反射黑箱；`shop_id` 条件容易在隐式查询里漏掉 |
| B. 只用静态 SQL 代码生成 | 所有查询写死在 `.sql` 中并生成类型安全代码 | 类型安全最好，但报表筛选条件组合无法穷举，最终仍要拼字符串 |
| C. **Go + 静态 SQL 生成 + 动态查询构建 + 显式事务（采用）** | 见下节 | 需维护 SQL 文件与手写场景专用 DTO，前期工作量大于 ORM；团队要能读懂 SQL 执行计划 |
| D. 动态语言运行时 + 全栈框架 | 快速出 CRUD | 常驻内存与冷启动成本高；金额精度要额外约束；长任务、设备长连接与高并发报表不够贴合 |

## 决策

| 分类 | 选型 | 理由（针对本项目约束） |
|---|---|---|
| 语言 | **Go 1.23+** | 标准库 `slog` / `slices` / `maps` 成熟，静态二进制部署小、冷启动快；并发模型适合设备长连接与报表并发 |
| Web 框架 | **Gin v1.10** | 路由分组清晰，中间件链适合统一注入门店范围与 request id |
| 接口风格 | **REST + OpenAPI**（`swaggo/swag`） | 前端与第三方集成门槛最低，契约可生成、可 diff；GraphQL / gRPC 的收益在本项目规模下不足以抵消复杂度 |
| 静态 SQL | **sqlc** | 写 SQL 生成类型安全代码，零反射；报表聚合与条件聚合可完整保留在 SQL 里 |
| 动态查询 | **squirrel** | 补 sqlc 无法覆盖的筛选组合；**PG 必须设 `PlaceholderFormat(squirrel.Dollar)`** |
| 数据库驱动 | **jackc/pgx/v5** | `numeric` / `timestamptz` / `jsonb` 映射精确，连接池与 `COPY` 支持好 |
| 迁移管理 | **pressly/goose** + **atlas** | goose 执行版本化迁移，atlas 检测 schema 漂移；禁止手工改库 |
| 金额 | **shopspring/decimal** | 定点十进制，与 PG `numeric` 对应，禁止 `float64` |
| 事务 | **自建 Unit of Work**（`*sql.Tx` 挂 ctx） | Go 无声明式事务，显式边界迫使巨型写方法被拆分 |
| 缓存 | **Redis + ristretto** | 跨实例与进程内双层，一律带 TTL 且写后失效 |
| 认证 | **golang-jwt/v5** + 服务端存储刷新令牌 | 短时效访问令牌；刷新后权限判定立即生效，不缓存跨店授权结果 |
| 密码 | **x/crypto/bcrypt** | 行业标准哈希，无需自研 |
| 参数校验 | **go-playground/validator v10** | 边界处统一校验，服务层不假设输入合法 |
| 配置 | **koanf v2** | 多源合并、无全局状态，启动时集中校验并快速失败 |
| 日志 | **log/slog**（标准库） | 结构化 JSON 直出，零依赖，贯穿 request id |
| 指标 / 追踪 | **prometheus/client_golang** + **OpenTelemetry** | 生产可观测性，跨服务链路可关联 |
| 定时任务 | **robfig/cron/v3** + **redsync** | 分布式锁避免多实例重复执行；后台任务幂等、可重试、有死信 |
| 实时能力 | **coder/websocket** | context 感知，心跳与断线重连可控 |
| Excel 导出 | **excelize/v2 `StreamWriter`** | 流式写出，避免全量读进内存 |
| 依赖注入 | **google/wire** | 编译期生成，无反射 |
| 测试 | **testing + testify + testcontainers-go** | 领域逻辑纯函数单测；集成测试起真实 PG 容器，不 mock 服务层 |
| 静态检查 | **golangci-lint** + **govulncheck** | 统一 lint 与依赖漏洞扫描 |
| 部署 | 多阶段构建 → `distroless/static` | 镜像小、攻击面小 |

R0 阶段的引导骨架（`cmd/porch-os`）只用标准库提供 `/health`，零外部依赖，目的是让 CI 具备可复现的编译与测试基线；上表依赖从 R1 起按模块逐步引入。

## 关键约束（代码评审阻断项）

1. **不建实体关联图**：领域结构体之间只持有 ID，不嵌套对方实体。
2. **一条查询返回一个场景专用扁平 DTO**；一对多折叠必须是 `internal/domain/` 下可脱离 DB 单测的纯函数。
3. **不使用数据库视图**：计算口径写在受版本控制的 SQL 中，视图会让口径失去唯一来源。
4. **动态查询必须设 `$1` 占位符格式**，且排序字段走白名单。
5. **金额一律 `decimal` / `numeric`**，禁止浮点类型。
6. **所有产生业务副作用的写操作提供幂等键**；单号唯一性靠数据库约束，且必须写明「店内唯一」还是「全局唯一」，不能靠应用层拼接。可用 PG 18 的 `uuidv7()` 生成时间有序单号。
7. **报表导出流式写出**，禁止 `readAll` 之后再返回。
8. **跨店权限判定结果不缓存**，刷新令牌后必须立即生效。
9. **集成测试用真实 PG 容器**，不为提速在集成测试里 mock 服务层。

## 明确不选

- **GORM / ent 作为主数据访问方式**：与第 1–3 条约束冲突；保留为未来局部工具的可选项，不进入主路径。
- **Viper**（全局状态）、**Fiber**（与已选中间件生态重叠）、**MongoDB**（与关系型报表与精确金额诉求冲突）。
- **把业务逻辑放进数据库视图、存储过程或触发器**。

## 后果与限制

- 正面：SQL 可见可控，报表与跨店汇总能用执行计划优化；`shop_id` 条件显式出现在每个查询里，隔离约束可被代码评审检查；静态二进制部署与冷启动适合小店低成本硬件。
- 代价：需要手写 SQL 与 DTO，CRUD 开发速度慢于 ORM；团队需具备 SQL 调优能力；自建 Unit of Work 与幂等机制需要自己维护边界。
- 约束：所有外部 SDK 必须能接受 context 并支持超时取消；客户端断开不能留下持续运行的服务端计算。
- 与 ADR-0001 的联动：若生产环境降级到 PG 17，需复查 `uuidv7()` 的应用层替代方案（17 无内置函数），其余选型不变。

## 不在本决策范围

- `porch-console` 的前端框架、API 客户端方案、组件库与 E2E 工具由该仓库独立决策；本决策只固定后端以 REST + OpenAPI 提供契约，不阻塞前端选型。
- 对象存储、短信、支付等外部集成的具体 SDK，随对应模块落地时另立 ADR；**打印已明确排除**，不设适配器（[ADR-0004](0004-scope-baseline.md)）。

## 复审条件

- 出现必须用图查询或全文检索才能表达的核心业务模型时；
- Go 版本或 `pgx` / `sqlc` 出现不兼容的重大变更时；
- 团队构成变化导致 SQL 维护成本不可接受时（此时重新评估方案 A，但须先给出隔离约束的等价保障）。
