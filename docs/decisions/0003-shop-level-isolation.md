# ADR-0003: 数据隔离只按门店层，不引入租户层

- 状态：已接受（2026-11-15）
- 决策问题：多店系统的数据隔离按几层建模，门店之上是否存在组织 / 租户层
- 影响范围：全部业务表 schema、查询与授权中间件、跨店汇总、前端门店上下文。与 [ADR-0001](0001-postgresql-18.md)（数据库）、[ADR-0002](0002-go-backend-stack.md)（后端技术栈）共同构成基础约束；本文是隔离模型的唯一权威定义

## 背景

Porch OS 面向「一个人开几家店」的小微经营者：所有门店属于**同一个经营主体**，共用一个数据库、一套用户体系与一份商品目录。跨店汇总、跨店会员是常见需求，但不存在「多个互不可见的客户组织共用一套系统」这种场景。

引入租户层会带来可量化的成本：每个查询多一层过滤条件、每个唯一约束要重新定义范围、跨店报表变成跨租户聚合、授权模型从「用户 ↔ 可见门店」变成「用户 ↔ 租户 ↔ 门店」两级。漏加任一层条件都只会静默返回错数据，让最危险的那一类错误组合翻倍。这些成本在本项目里没有对应收益。

## 备选方案

| 方案 | 描述 | 代价 |
|---|---|---|
| A. 租户层 + 门店层（两层） | `tenant_id` + `shop_id`，租户隔离叠加门店维度 | 多一层过滤与授权；唯一性范围复杂化；跨店汇总要跨租户；对单一经营主体是纯冗余 |
| B. **仅门店层（采用）** | 只有 `shop_id`，单库单 schema、一个经营主体 | 无法在同一实例上服务互不可见的多个客户组织——本项目明确不做 SaaS |
| C. 门店层 + 物理隔离 | 每店独立 schema 或数据库 | 跨店汇总要跨库聚合，迁移与连接管理成本陡增 |
| D. 依赖数据库 RLS | 用行级安全策略按会话变量过滤 | 隔离条件变成隐式上下文，代码评审与 `EXPLAIN` 都看不见；与「默认查询显式带门店条件」直接冲突 |

## 决策

**数据隔离只有一层：`shop_id`。** 不存在 tenant / org / company / 集团等上层维度，也不把它们作为数据归属、授权边界或查询条件。

1. 单库、单 schema、一套用户体系；所有业务表带 `shop_id`，复合索引与唯一约束以它为前导列。
2. **禁止**任何 `tenant_id` / `org_id` / `company_id` 列，禁止 schema-per-shop、禁止按会话变量做 RLS 过滤、禁止 tenant scope 中间件；引入这类字段或中间件的 PR 直接拒绝。
3. `ShopGroup` 是**汇总与授权的分组标签**，不是数据归属层：一条业务记录始终只属于一个 `shop_id`，不会「属于」某个店群。
4. 跨店共享实体（会员档案、商品目录等）不带隔离维度、全局唯一；其**产生业务副作用的数据**（余额变动、消费流水、库存、单据）必须带 `shop_id`。跨店核销是一次显式业务动作，不是提升一层数据权限。
5. 跨店查询 = 在「当前用户可见的门店集合」上做聚合，必须显式声明并单独授权；它不是跨租户查询，也不产生新的数据副本。
6. 授权模型是「用户 ↔ 可见门店集合」的**直接关系**，由认证主体推导，不经过任何上层实体；跨店权限判定结果不缓存。
7. 隔离条件必须**显式出现在 SQL 与调用链里**，便于代码评审与执行计划检查；服务层入口注入的是 shop scope，不是 tenant scope。

## 理由

1. **与业务事实一致**：所有门店同属一个经营主体，没有互不可见的客户组织需要隔离。
2. **减少一类静默错误**：漏加 `shop_id` 已经是最危险的错误，再加一层只会让错误组合翻倍。
3. **跨店汇总保持简单**：一层维度下，汇总就是对 `shop_id` 做 `GROUP BY` / `FILTER` / 条件聚合。
4. **唯一性范围可明确表述**：只需区分「店内唯一」与「全局唯一」，不必再定义「租户内唯一」。
5. **与 SQL 优先一致**（ADR-0002）：条件写在 SQL 里看得见，RLS 的隐式上下文与之相悖。

## 后果与限制

- **明确放弃 SaaS 化**：将来若要服务多个互不可见的经营主体，必须新建 ADR 重新设计隔离模型，不能靠「加一个 `tenant_id` 列」渐进改造——那会漏改所有历史查询。
- 会员档案等全局实体需要在服务层处理跨店冲突（例如同一手机号在两店的记录合并），不能靠隔离维度自动解决。
- 数据删除与导出按 `shop_id` 组织；不存在「按租户清库」这类操作。业务数据暂不归档、不设保留窗口（[ADR-0004](0004-scope-baseline.md)），但导出仍需按店分列、跨店导出需显式授权。
- 所有 schema 变更与查询类 PR 都要按第 2 条检查；评审清单见 [`../ARCHITECTURE.md`](../ARCHITECTURE.md) 第 2.0 节与 PR 模板。

## 复审条件

- 出现「同一套系统服务多个互不可见经营主体」的真实需求；
- 出现法规要求按法人主体做物理隔离。
