# ADR-0004: 业务范围基线（单币种、东八区、暂不归档、不打印、不离线）

- 状态：已接受（2026-11-15）
- 决策问题：R1 业务代码开工前，把 [`../design/00-overview.md`](../design/00-overview.md) 第 8 节中四项影响地基的开放问题（OQ-01 / OQ-02 / OQ-03 的打印部分 / OQ-06）定下来，避免默认假设被当成结论
- 影响范围：schema、领域值对象、API 契约、前端展示、后台任务与部署配置；本文是这五项口径的**唯一权威定义**，[`../ARCHITECTURE.md`](../ARCHITECTURE.md) 与 `design/00`–`06` 与本文冲突时以本文为准
- 上游：[ADR-0001](0001-postgresql-18.md)（PG 18.7）、[ADR-0002](0002-go-backend-stack.md)（SQL 优先）、[ADR-0003](0003-shop-level-isolation.md)（只有 `shop_id` 一层）

## 背景

详细设计初版为了不阻塞评审，对四个问题写了默认假设：单币种 + 门店时区展示、在线保留 24 个月后归档、R1 不接外部服务、不支持离线收银。这些假设分别会改变金额类型、时间字段与业务日算法、分区与保留策略、外部适配器清单、以及一致性模型；任意一条写错，代价都是 R1 之后改 schema 或改契约。因此需要把它们从「假设」升格为「决策」，并明确哪些能力**明确不做**。

本决策只处理范围收窄，不改变三条上游 ADR 的任何技术选型。

## 备选方案

| 议题 | 方案 A（采用） | 方案 B | 方案 C |
|---|---|---|---|
| 币种 | 单一币种 CNY，金额列不带币种 | 金额带 `currency`，预留多币种与汇率 | 金额带币种 + 每日汇率表与折算报表 |
| 时区 | 统一 UTC+8（`Asia/Shanghai`），无门店级时区 | 每店可配时区，UTC 存储 + 按店展示 | 全链路本地时间（去 `timestamptz`） |
| 数据保留 | 业务数据在线全量保留，暂不归档、不分区 | 在线保留 24 个月，更早按 `shop_id` 归档 | 按月声明式分区 + 冷热分离 |
| 打印 | 不支持，不提供打印端点与设备适配 | 服务端生成小票模板 + 打印网关抽象 | 前端直连本地打印机驱动 |
| 离线 | 不支持离线收银，全程在线强一致 | 本地队列缓存写操作，恢复后补传 | 本地完整副本 + 双向同步与冲突合并 |

B/C 的共同代价：需要额外的列或表、额外的口径校验、额外的测试矩阵；C 还会把「写入是否生效」从确定性变成最终一致，直接冲击 [ADR-0002](0002-go-backend-stack.md) 的幂等与事务边界设计。这些成本目前没有对应需求。

## 决策

### 1. 单币种，人民币（CNY）

1. 全系统只有一种货币：CNY，展示符号 `¥`；金额列一律 `numeric(14,2)`，**不设 `currency` 列**。
2. 领域值对象 `Money` 只含 `amount decimal`，不含币种字段；不做币种一致性校验、不做换算、不存汇率、不产出折算报表。
3. API 金额仍用字符串传输（`"19.90"`），响应中不带币种字段；接口与文档统一以 `¥` 标注金额。

### 2. 统一东八区（UTC+8）

1. 存储与传输不变：`timestamptz` 内部 UTC，API 时间用 ISO 8601 UTC（`2026-11-01T00:00:00Z`）；区间一律半开 `[start, end)`。
2. **展示、业务日、单号日期统一按 `Asia/Shanghai`（UTC+8）**，不做门店级时区配置，不接受客户端传入的时区参数。
3. 业务日口径：`business_date = (occurred_at AT TIME ZONE 'Asia/Shanghai')::date`；营业日切点作为门店业务参数留在 `shop_settings`（默认 00:00，可按店配置偏移），但**基准时区不可按店覆盖**。日报、班次、汇总、导出都按同一口径。
4. 全局配置固定 `APP_TIMEZONE=Asia/Shanghai`，启动时校验；容器与数据库会话时区同步设为该值，便于人工查库时读数一致。`timestamptz` 的 UTC 语义不受会话时区影响。

### 3. 业务数据暂不归档

1. 在线全量保留业务数据：不设保留年限、不做分区、不导出历史归档、不提供「归档数据专用查询」路径。
2. 日报等派生数据照常预聚合与重算（`design/05` 第 8 节），这是读模型，不是归档。
3. **运行期清理不等于归档**：`idempotency_keys` 过期键、已投递且超期的 `outbox_events`、失败的导出临时文件仍按既定 TTL 清理；它们不是业务事实，不清理会拖垮库。业务单据与流水不参与这类清理。
4. 容量靠索引、预聚合、keyset 分页与流式导出扛住；把表膨胀、慢查询比例、库体积列为监控指标，达到阈值时**另立 ADR** 再评估分区或归档，不在代码里悄悄加保留窗口。

### 4. 不支持打印

1. 不提供打印端点、小票模板、打印任务、打印机/驱动适配，也不在 `adapter/gateway/` 下预留打印适配器。
2. 前端不出现打印入口。**导出（Excel / CSV 文件下载）不受影响**，仍按 `design/03` 第 8 节的异步导出端点实现。
3. 需要纸质凭证时由使用方自行下载导出文件后处理，这属于系统外行为。

### 5. 不支持离线收银

1. 所有写操作在线同步完成，单库事务强一致；不做本地队列、断网缓存、恢复补传、冲突合并、设备时钟校正或最终一致性对账。
2. 网络失败即返回明确错误，前端只提示「网络不可用」并保留已填内容，**不允许在离线状态下继续提交单据**；恢复后由用户重新发起请求，幂等键照旧防重复。
3. 因此不需要本地存储、设备级单号段、同步水位或补偿任务；`design/05` 的幂等、Outbox 与事务边界保持不变。

## 理由

1. **减少一类静默错数据**：币种与时区一旦可配，「同一个金额是不是同一种钱」「这一天算哪天」就会在报表里出现不报错的偏差，与 ADR-0003 拒绝上层维度是同一条思路。
2. **口径唯一**：单一时区让 `business_date`、单号日期、班次、日报、导出共用一条公式，纯函数可表驱动测试；单币种让计价与分摊只需验证数值，不必验证币种组合。
3. **地基成本最低**：不归档就不必引入分区键（PG 声明式分区要求唯一约束包含分区键，会与「`(shop_id, order_no)` 店内唯一」及复合外键冲突，见 `design/02` 第 7 节）；不打印就不必引入外部 IO；不离线就不必把一致性降级。
4. **范围明确而非能力缺失**：三条「不支持」写进决策记录，是为了让贡献者与前端对接方不再按默认假设各自脑补，也避免把「网络失败提示」误解成「离线可用」。

## 后果与限制

- 将来支持多币种、多时区门店、法定票据打印或断网收银，属于**范围扩展**，必须新建 ADR 并重新评估 schema 与契约；不能靠「加一列 `currency`」「加一个时区参数」「加一个本地队列」渐进塞进来——历史查询与历史数据都要重算。
- 单币种下「跨币种比较」「汇率折算」类校验从评审清单移除，但金额禁用浮点、`numeric(14,2)`、`ROUND_HALF_UP` 的约束**不变**（`design/01` 第 6、9 节）。
- UTC+8 与 UTC 的换算只在展示层与业务日计算处发生；所有 `AT TIME ZONE` 都显式写 `'Asia/Shanghai'`，不依赖数据库会话默认，避免部署环境差异改变报表结果。
- 全量保留意味着数据量只增不减：需要监控 `orders` / `payments` / 流水表的膨胀与索引体积，并把「大表 `Seq Scan`」继续作为 PR 阻断项（`design/02` 第 5 节）。
- `design/00` 第 8 节的 OQ-01 / OQ-02 / OQ-03（打印部分）/ OQ-06 随之关闭；其余开放问题（OQ-03 的其他外部集成、OQ-04 前端框架、OQ-05 部署形态、OQ-07 跨店差额、OQ-08 审计合规）继续待确认。

## 复审条件

- 出现境外门店、多币种结算或跨时区连锁经营的真实需求；
- 单表行数或库体积达到预设容量阈值（阈值在 R1 压测后确定并写入运维清单），全量保留不再经济；
- 法规或经营场景要求出具机打票据，或要求断网期间必须能完成收银；
- 上游 ADR-0001 / 0002 / 0003 任一被修订且影响本决策的口径。
