# ADR-0005: 取消门店组概念，跨店能力改用显式门店集合

- 状态：已接受（2026-11-15）
- 决策问题：多店系统是否需要「门店组 / 店群」这一分组实体，用于汇总与授权
- 影响范围：领域模型、schema 表清单、API 端点与权限码、授权判定链、前端门店切换与报表视图。本文**修订 [ADR-0003](0003-shop-level-isolation.md) 第 3 条**（该条原将 `ShopGroup` 定义为汇总与授权的分组标签），ADR-0003 其余条款不变；与 [ADR-0004](0004-scope-baseline.md) 同属范围收窄类决策。本文是「是否存在门店分组」的唯一权威定义。
- 上游：[ADR-0001](0001-postgresql-18.md)（PG 18.7）、[ADR-0002](0002-go-backend-stack.md)（SQL 优先）、[ADR-0003](0003-shop-level-isolation.md)（只有 `shop_id` 一层）、[ADR-0004](0004-scope-baseline.md)（范围基线）

## 背景

详细设计初版把 `ShopGroup` 当作通用多店底座的一部分：ADR-0003 第 3 条将其定义为「汇总与授权的分组标签、不是数据归属层」，`design/02` 落了 `shop_groups` / `shop_group_members` 两张表，`design/03` 落了店群列表与成员调整两个端点，README 与 ARCHITECTURE 的术语表也把它列为正式术语。

用户明确确认：**不需要门店组概念**。此时处于 R0，业务代码尚未开始，数据库只有设计文档里的 DDL 节选，删除分组实体的成本最低；一旦 R1 把表、路由与授权链写进代码，再拆就要改 schema 与契约。

需要先澄清一个容易混淆的点：取消的是**分组实体**，不是**跨店能力**。「能同时管理多个门店」「单店独立核算、跨店汇总对比」仍是产品定位（见 README），只是不再经过「组」这层间接对象。

## 备选方案

| 方案 | 描述 | 代价 |
|---|---|---|
| A. **完全移除（采用）** | 不设 `ShopGroup`；跨店汇总用可见门店集合 + 显式 `shop_ids` 表达 | 门店数量很大时，每次跨店请求要显式列出门店；前端多选负担上升 |
| B. 保留纯展示标签 | 保留 `shop_groups` 只做报表分组展示，不参与授权 | 仍要维护「组 ↔ 成员」关系的一致性（成员增删、组删除、缓存失效）；两套报表口径（按店 / 按组）需要长期对齐 |
| C. 保留完整店群（标签 + 成员 + 授权） | 维持初版设计 | 授权从「用户 ↔ 门店」变成「用户 ↔ 组 ↔ 门店」两级，与 `user_shops` 并列形成两套授权来源；组成员变更会让跨店结果静默变化，且可能出现「通过组看到本无权门店」的越权路径 |

B/C 的共同问题：分组一旦可持久化，就必然要回答「谁维护它」「它是否参与权限判定」「成员变更后历史报表怎么算」三个问题；而当前系统的门店规模是「一个人开几家店」，这些问题没有对应收益。

## 决策

**不设门店组 / 店群 / 任何等价分组实体；跨店能力全部由显式门店 ID 集合表达。**

1. **删除分组实体**：不设 `ShopGroup`（及 `ShopGroupMember`），删除 `shop_groups`、`shop_group_members` 两张表；`shops` 表不带任何分组、层级或标签列。
2. **删除接口与权限**：不提供 `/api/v1/shop-groups*` 端点、店群成员管理、店群权限码与店群相关前端页面；不设店群切换器。
3. **禁止等价替代物**：不得用 `parent_id` 自引用、`group_id`、`shop_set`、`shops.tag`、`scope=group:...`、按标签筛选参数等其他名字把分组塞回来。`Chain` / `Franchise` / `Outlet` / `Branch` 等术语继续按 ADR-0003 禁用。R1 起代码、表、列、路由、DTO 中不允许出现 `shop_group` 命名。
4. **授权唯一来源**：`user_shops` 是「可见门店集合」的唯一来源，由认证主体每次请求实时推导，不缓存；`report.cross_shop` 等显式权限点是跨店读的唯一开关。不存在「按组授权」。
5. **跨店读**：`scope=all` 或 `shop_ids=a,b` 指定范围，仍需跨店权限，且请求中的门店列表必须与可见集合求交，越权项直接拒绝而非静默忽略；报表按 `shop_id` 分组，不按组分组。
6. **跨店写**：调拨、跨店核销等仍是专用端点 + 单独权限 + 两端门店都在可见集合内的显式动作，与 ADR-0003 第 4–6 条一致。
7. **门店集合不是可持久化对象**：`scope=all` 是「当前主体此刻可见的全部门店」的即时集合，不生成 ID、不落表、不存历史、不复用。「常用门店组合」若将来实现，只能是前端/用户级展示偏好，不得成为后端实体，也不得参与权限判定。
8. **隔离模型不变**：数据隔离仍只有 `shop_id` 一层；禁止 `tenant_id` / `org_id` / `company_id`、schema-per-shop、按会话变量 RLS。ADR-0003 第 3 条由本条取代，其余 1、2、4、5、6、7 条继续有效。

## 理由

1. **与规模匹配**：目标用户是开几家店的小微经营者，门店数量小，前端多选门店比维护一组长期有效的分组关系更直接；分组层是为几十上百家店准备的间接层。
2. **少一条越权路径**：组若参与授权，判定链变成「主体 → 组 → 门店」，与 ADR-0003 拒绝上层维度是同一条思路；组成员一变，跨店结果会在不报错的情况下变化。
3. **授权口径唯一**：只有 `user_shops` + `report.cross_shop` 一处口径，代码评审、`EXPLAIN` 与集成测试只需检查一条链路，不会出现两套权限来源不一致。
4. **降低地基成本**：少两张表、两个端点、一组权限码、一套成员一致性测试与缓存失效逻辑；R1 的迁移与契约面同步收窄。
5. **与 ADR-0004 一致**：同样是把未被证实需要的通用能力从底座里拿掉，避免贡献者按默认假设各自脑补；且 R0 删除无历史数据迁移成本。

## 后果与限制

- **跨店汇总、跨店对比、跨店导出能力不变**，只是每次显式指定门店范围；`design/05` 的报表三层读模型与 `design/06` 的 F-05 流程不需要改结构，只去掉「按组」这一可能的理解。
- 门店数量增长后，UI 需要更好的多选/搜索体验；「保存常用选择」属于展示偏好，不作为后端对象。
- `design/00` 第 8.1 节新增本条已确认决议；当时剩余开放问题为 5 个（OQ-03 其余、OQ-04、OQ-05、OQ-07、OQ-08），**其后已由 [ADR-0007](0007-remaining-open-questions.md) 全部关闭**。7 项设计提案 DP-01–07 **已由 [ADR-0008](0008-design-freeze-and-nq-resolutions.md) 接受**，整套详细设计**已冻结**（历史状态订正，本文条款不变）。
- ADR-0003 的修订以顶部「修订记录」标注，正文第 3 条已改写；历史提交仍可通过 git 追溯，不影响「隔离模型唯一权威」的定位。
- 「一个用户可关联多间门店」与「当前门店可切换」由 [ADR-0006](0006-user-shops-and-current-shop.md) 定义；切换只是选择可见集合中的一个元素，不改变本 ADR 第 5、7 条的跨店范围表达，也不重新引入分组对象。
- 将来若要按区域、业态、加盟体系做固定分组汇总或分组授权，属于**范围扩展**：必须新建 ADR，先复审 ADR-0003 的隔离模型，并重新评估历史报表口径；不能靠「给 `shops` 加一列 `group_id`」渐进塞进来。

## 复审条件

- 单一经营主体的门店规模增长到分组管理成为刚需（R1 压测后给出具体阈值，暂定 > 30 家店且报表需按固定分组出数）；
- 出现按组织 / 加盟 / 区域划分授权边界的真实需求（此时优先复审 ADR-0003）；
- 上游 ADR-0001 / 0002 / 0003 / 0004 任一被修订且影响本决策的口径。
