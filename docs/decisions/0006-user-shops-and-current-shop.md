# ADR-0006: 用户可拥有多间门店，当前门店是可切换的请求期上下文

- 状态：已接受（2026-11-15）
- **修订记录（2026-11-15）**：[ADR-0008](0008-design-freeze-and-nq-resolutions.md)（NQ-02）确认本文关系为 **`user_shops` 多对多**，关闭下方悬置假设；正文条款、schema 与切换协议均不变。
- 决策问题：用户与门店的关系基数如何建模；页面切换门店时「当前门店」是什么、由谁决定、切换会改变什么
- 影响范围：`user_shops` schema、认证与授权中间件、登录 / `/me/shops` 契约、`X-Shop-Id` 处理规则、前端门店切换器、缓存键与在途请求、集成测试清单。本文**不新增隔离维度**，[ADR-0003](0003-shop-level-isolation.md) 仍是隔离模型的唯一权威定义；跨店范围仍按 [ADR-0005](0005-no-shop-groups.md) 用显式门店集合表达。
- 上游：[ADR-0002](0002-go-backend-stack.md)（JWT 不放权限/门店清单、判定不缓存）、[ADR-0003](0003-shop-level-isolation.md)（只有 `shop_id` 一层）、[ADR-0004](0004-scope-baseline.md)（范围基线）、[ADR-0005](0005-no-shop-groups.md)（无分组对象、授权唯一来源）

## 背景

用户明确确认：**用户和门店为 1 对多关系，一个用户可以拥有多间门店，可以在页面进行切换**。

详细设计初版其实已经具备多店的骨架：`user_shops` 关系表、`ShopScope`（可见门店集合）、`GET /api/v1/me/shops`（切换器数据源）、`X-Shop-Id` 请求头，以及 `porch-console` 的「全局门店上下文」。但口径散落在 `design/00`–`06` 与两个仓库里，且有三处会直接导致返工：

1. **`03` 第 3 节把多店当例外**：「未带 `X-Shop-Id`：可见集合恰有 1 家 → 默认该店；多店且无跨店权限 → `400 SHOP_CONTEXT_REQUIRED`」。按新口径，一个账号默认就能管好几家店，第一次打开页面就撞 400 是不可接受的；而且「隐式落到唯一那家店」在授权变更后是串店风险。
2. **「当前门店」没有身份定义**：它是服务端会话状态、JWT claim、还是客户端上下文？切换是否要发写请求、是否改变权限、是否需要新端点？没定就会各自脑补。
3. **切换的副作用没写**：在途请求带着旧门店头返回后覆盖新页面、缓存键不带 `shop_id`，都会造成「切到 B 店却显示 A 店数据」——这正是 `design/00` 质量属性第 1 条要防的静默错数据。

此时处于 R0，业务代码尚未开始，接口契约仍是设计提案，收敛这些口径的成本最低。

### 术语澄清（本 ADR 最容易被误读的一处）

| 说法 | 准确含义 |
|---|---|
| 「用户和门店是 1 对多」 | **从当前主体视角**看：一个账号登录后能管理 N 家店（N ≥ 0）。这是产品事实，不是表结构的基数定义 |
| 数据关系 | 仍是 **`user_shops` 多对多**：同一家店也会被多个账号访问（经营者、店员、管理员）。因此**不能**实现成 `users.shop_id` 外键或 `shops.owner_user_id` 单列 |
| 「拥有」 | 统一理解为**可见 / 可管理（授权）**，不是数据所有权。业务数据的归属仍只有 `shop_id`（ADR-0003）；用户不「拥有」店里的单据、库存与余额 |
| 「切换」 | 只改变**当前正在看哪家店**这个上下文，不改变可见门店集合、角色权限、数据归属，也不产生服务端写入 |

## 备选方案

| 方案 | 描述 | 代价 |
|---|---|---|
| A. **多对多关系 + 请求期上下文（采用）** | `user_shops` 表达「一人多店 / 一店多人」；客户端保存当前门店并在每次单店请求显式携带，服务端每次与可见集合求交校验；登录返回门店列表与默认门店 | 客户端必须统一注入门店头，漏带即 400；当前门店是本地状态，多设备不同步 |
| B. 服务端记住当前门店 | 新增 `user_sessions.current_shop_id` 或偏好表，切换变成一次写请求 | 引入服务端可变状态；切换要处理幂等与并发覆盖；授权变更时要同步失效，和「判定不缓存、下一个请求即生效」相冲突；与 JWT 无状态设计背道而驰 |
| C. 严格 1:N，`users.shop_id` 单外键 | 一个账号一家店，切换靠 `UPDATE users` | 一家店只能有一个账号，无法表达店员 / 多账号；切换是写操作且并发互相覆盖；撤销授权要改用户记录，没有独立授权来源 |
| D. 把门店清单与当前门店写进 JWT | 切换无需请求，前端解析令牌即可 | 授权变更要等令牌过期才生效，直接违反 ADR-0002 阻断项 ⑧ 与 `design/05` 第 1 节；门店清单还会随令牌泄露给客户端当作权限依据 |

## 决策

**一个用户可关联多间门店（关系实现为 `user_shops` 多对多）；「当前门店」是客户端持有、服务端每次校验的请求期上下文，可在页面随时切换。**

1. **关系基数与 schema**：
   - `user_shops(user_id, shop_id)` 是唯一授权来源，主键 `(user_id, shop_id)`，保留 `(shop_id, user_id)` 反向索引；一个用户可有 N 家店，一家店也可被 N 个用户访问。
   - **`users` 不加 `shop_id` / `current_shop_id`；`shops` 不加 `owner_user_id` / `owner_id`**；不设 `current_shops`、`user_preferences` 之类的当前门店表或偏好表。不引入「店主账号」这类新授权层级。
   - 可见门店集合允许为空（新账号尚未授权）：登录成功但 `default_shop_id` 为 `null`，前端显示「暂无可用门店」的可读提示，不出现空白页，也不放行任何单店请求。
2. **当前门店的身份**：请求期上下文，**不是持久化实体、不落表、不进 JWT、不作为授权来源**。每次单店业务请求显式带 `X-Shop-Id`（`public_id`，与路径 `{shopId}` 一致时以路径为准且两者必须相同）；服务端用 `user_shops` 实时推导的可见集合求交。
3. **登录与门店列表**：
   - `POST /api/v1/auth/login` 在令牌之外返回 `shops`（可见集合：`public_id`、`name`、`status`）与 `default_shop_id`。
   - `default_shop_id` 由服务端按确定性规则给出：可见集合中 `status = active` 且 `granted_at` 最早的店；集合为空则 `null`。客户端可把「上次选择」覆盖上去，但**必须校验它仍在最新可见集合内**，否则丢弃并回退到 `default_shop_id`。
   - `GET /api/v1/me/shops` 是切换器的权威数据源，进入应用、刷新页面、重新登录、收到 `403` 时都要重新拉取；前端不得把它当作永久权限依据缓存。
4. **`X-Shop-Id` 规则（修订 `design/03` 第 3 节）**：
   - 单店业务请求**必须显式**携带当前门店；缺失 → `400 SHOP_CONTEXT_REQUIRED`。不再按「可见集合恰有 1 家」隐式默认——漏带应该是明确报错，而不是静默落到另一家店。
   - 未命中可见集合、门店已停用或授权已撤销 → `403 PERMISSION_DENIED`；不区分「门店不存在」与「无权访问」，防枚举。
   - 例外：`/auth/*`、`/api/v1/me*`、`/health`、`/ready` 不需要当前门店；跨店聚合用 `scope=all` + `shop_ids` 表达范围，也不依赖当前门店。
5. **页面切换协议**（`porch-console` 必须实现，`design/03` 第 7 节与 `design/06` F-07 落地）：
   - 切换器选项只来自 `GET /me/shops`；不接受本地伪造或 URL 传入的门店 ID。
   - 切换 = 更新本地「当前门店」 + 后续请求改带新 `X-Shop-Id`。**不新增端点**（没有 `POST /me/current-shop`）、不写服务端、不改变权限、不改变数据归属。
   - 切换前取消所有在途的单店请求；无法取消时丢弃来自旧门店的响应（响应体带 `shop_id`，渲染前与当前门店比对）。
   - 所有派生查询与缓存以 `(user_id, current_shop_id, query_key)` 为键失效重取；跨店视图按显式 `shop_ids` 单独缓存，**不受当前门店切换影响**。
   - 重新拉取 `/me/permissions`；无权限时给可读提示而非空白页。当前门店被撤销或停用时自动回退到 `default_shop_id`，禁止停留在无权门店。
   - 「当前门店」可存 localStorage（它不是令牌、不是权限依据），刷新后恢复；恢复时必须用最新 `/me/shops` 复核。
6. **服务端保持无状态**：`user_shops` 每次请求实时推导，判定结果不缓存；授权变更仍在**下一个请求**生效（F-06）。切换本身不触发任何授权重算。
7. **切换与跨店汇总解耦**：切换器只管「单店视图看哪家」；跨店汇总 / 对比 / 导出由 `scope=all` + 显式 `shop_ids` + `report.cross_shop` 决定（ADR-0005），不因切换而缩小或扩大，也不是分组选择器。
8. **隔离模型不变**：数据隔离仍只有 `shop_id` 一层；不引入 `tenant_id` / `org_id` / `company_id`、schema-per-shop、RLS（ADR-0003），不引入门店组或任何等价分组对象（ADR-0005）。切换只是选择集合中的一个元素。

## 理由

1. **多店是常态而非例外**：目标用户是「一个人开几家店」，切换是第一等交互；把当前门店做成请求期上下文，服务端无需状态，和短时效 JWT + 实时授权推导一致。
2. **M:N 是唯一同时成立的形状**：既能「一人多店」，也能「一店多人」。方案 C 的单外键会把账号锁死在单店，且让店员账号无法实现。
3. **显式优于隐式**：强制 `X-Shop-Id` 把「漏带」变成 400，而不是悄悄查询默认店；授权撤销后旧头立即 403。直接对应 `design/00` 质量属性第 1 条。
4. **切换零写入**：不落库就没有并发覆盖、幂等、迁移与新端点成本；也没有一处需要额外失效的服务端状态，F-06 的「立即生效」不被破坏。
5. **防住最典型的串店事故**：缓存键含 `shop_id`、在途请求取消 / 陈旧响应丢弃，这两条不写进契约，前端框架选型时几乎必然漏掉。

## 后果与限制

- 客户端必须统一封装并注入 `X-Shop-Id`；漏带返回 `400 SHOP_CONTEXT_REQUIRED`。该错误码的**触发范围由「多店未指定」扩大为「单店请求未指定」**，语义不变，属于已冻结契约的一部分，必须同步 `porch-console` 与 OpenAPI。
- 当前门店是本地状态，多设备 / 多标签页各自独立，这是有意的取舍；收敛方式是刷新或重新可见时重拉 `/me/shops`。新设备首次登录落到 `default_shop_id`。
- 不提供「记住上次门店到服务端」的能力；将来若要做跨设备记忆，需另立 ADR，且该偏好只能是展示偏好，**不得参与权限判定**（与 ADR-0005 第 7 条一致）。
- `design/00` 第 8.1 节新增本条已确认决议；当时剩余开放问题为 5 个（OQ-03 其余、OQ-04、OQ-05、OQ-07、OQ-08），**其后已由 [ADR-0007](0007-remaining-open-questions.md) 全部关闭**。7 项设计提案 DP-01–07 **已由 [ADR-0008](0008-design-freeze-and-nq-resolutions.md) 接受**，整套详细设计**已冻结**；本文关系基数假设亦由 ADR-0008（NQ-02）确认。
- **已确认（ADR-0008 / NQ-02）**：用户明确选择**多对多**——本文「术语澄清」的「主体视角 1:N + `user_shops` 多对多」为最终口径，schema、`X-Shop-Id` 协议与切换流程**零改动**。严格 1:N（一店一账号、`users.shop_id` 外键）方案已排除，不再作为待确认项；将来若要改，须新 ADR 并重做授权模型。
- 新增 `design/06` F-07「门店切换」流程与四类测试；`design/02` 的约束测试增加「`users` / `shops` 无单店外键或 owner 列」断言。ADR-0003 / ADR-0005 仅加交叉引用，正文条款不变。
- 若将来出现「按门店分别授予不同角色」的需求，会改变 `user_shops` 的语义，必须先复审 ADR-0003 第 6 条，不能靠在关系表里加 `role_id` 渐进扩展。

## 边界澄清

评审时不得混用以下三组：

- **一人多店 ≠ 一店一人**：不能据此把 `user_shops` 改成 `users.shop_id` 外键。
- **当前门店 ≠ 授权来源**：切换不改变可见门店集合；服务端每次仍用 `user_shops` 求交校验。
- **页面切换 ≠ 跨店汇总**：切换器只选单店视图的上下文；跨店范围由显式 `shop_ids` 与跨店权限决定。

## 复审条件

- 单一账号需要在极多门店间切换（R1 压测后给出阈值，暂定 > 50 家），前端需要服务端偏好、搜索或分页门店列表；
- 出现跨设备同步「上次门店」的强需求，或需要按门店分别授予不同角色；
- 上游 ADR-0002 / 0003 / 0004 / 0005 任一被修订且影响授权推导或门店上下文口径；
- NQ-02 决议被推翻（改为严格 1:N 的 `users.shop_id` 外键）。
