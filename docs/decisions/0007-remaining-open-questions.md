# ADR-0007: 剩余开放问题决议（外部集成、前端框架归属、编排平台部署、跨店差额、审计日志保留）

- 状态：已接受（2026-11-15）
- 决策问题：把 [`../design/00-overview.md`](../design/00-overview.md) 第 8.2 节仅剩的五个开放问题（OQ-03 其余 / OQ-04 / OQ-05 / OQ-07 / OQ-08）定下来，使**全部 OQ 关闭**、详细设计具备冻结前提
- 影响范围：外部适配器边界、`porch-console` 的选型归属、部署形态与进程假设、跨店账务口径、`audit_logs` 的保留与清理任务、监控与配置。本文**修订 [ADR-0004](0004-scope-baseline.md) 第 3 节第 3 条的运行期清理清单**，其余条款不变
- 上游：[ADR-0002](0002-go-backend-stack.md)（技术栈与阻断项）、[ADR-0003](0003-shop-level-isolation.md)（只有 `shop_id`）、[ADR-0004](0004-scope-baseline.md)（范围基线）、[ADR-0005](0005-no-shop-groups.md)（无门店组）、[ADR-0006](0006-user-shops-and-current-shop.md)（当前门店是请求期上下文）

## 背景

用户一次性确认：OQ-03 确认、OQ-04 确认、OQ-05 支持编排平台且暂时不读写分离、OQ-07 确认、OQ-08 确认且**审计日志定时删除、只保留 30 天、支持配置**，并要求列出仍需确认的问题。

这五条在初版详细设计里都只有「默认假设」，其中三条会直接改变地基：

1. **OQ-08 与既有文档冲突**：初版假设是「审计日志追加写、不可更新/删除」，`design/02` 第 7 节甚至写了「审计日志不设保留年限」，`design/05` 第 11 节写了「不可更新删除」。新口径要求定时物理删除，必须重新界定「不可变」的语义边界，并把审计日志从「业务数据全量保留」的清单里摘出来。
2. **OQ-05 覆盖默认假设**：初版写「先单机 Compose、重报表走预聚合」。支持编排平台意味着 `api` / `worker` 必须无状态、可水平扩缩，迁移不能由每个 Pod 各自执行，定时任务在多副本下不能重复跑，连接池上限要按副本数推导——这些都是单机假设下不需要回答的问题。
3. **OQ-04 的「确认」只确认了归属**：默认假设是「由 `porch-console` 独立决策，后端只保证 REST + OpenAPI」。确认它并不等于选定了某个前端框架；具体框架仍需由前端仓库决策（见下方「仍需确认」）。

此时业务代码尚未开始，schema 与接口仍是设计提案，改口径没有历史数据迁移成本。

### 理解澄清（最容易被误读的三处）

| 说法 | 准确含义 |
|---|---|
| 「OQ-04 确认」 | 确认**决策权归属**：前端框架由 `porch-console` 独立决策、后端不绑定框架。**具体框架 / API 客户端 / 组件库仍未选定**，不阻塞后端，但仍是待确认项 |
| 「支持编排平台」 | 应用可按容器编排平台部署、可水平扩缩；**不等于拆微服务**，模块化单体（DP-01）不变，也不等于引入服务网格或多套数据库 |
| 「审计日志保留 30 天」 | 只针对 `audit_logs` 这张**基础设施表**的运行期数据；**不是**业务数据归档，也**不是**允许业务请求删除单据、流水或审计记录 |

## 备选方案

| 议题 | 方案 A（采用） | 方案 B | 方案 C |
|---|---|---|---|
| OQ-03 外部集成 | R1 不接外部服务，只留网关接口骨架；具体 SDK 与投递目标随模块落地时另立 ADR | R1 就接支付 / 短信 / 对象存储 | 全部外部调用走统一 ESB / 集成平台 |
| OQ-04 前端框架 | 由 `porch-console` 独立决策，后端只保证 REST + OpenAPI | 后端仓一并指定前端框架与代码生成方式 | 用 BFF 把前端框架差异吸收到后端 |
| OQ-05 部署 | 支持编排平台，`api` / `worker` 无状态水平扩缩；单主库、暂不读写分离 | 仅单机 Compose，靠纵向扩容 | 编排平台 + 读写分离 / 只读副本扛报表 |
| OQ-07 跨店差额 | 只记录消费发生在哪家店，不做自动清分 | 引入内部往来账与定期结算单 | 实时跨店清分，消费时即转移门店间债权 |
| OQ-08 审计日志 | 默认保留 30 天、可配置、worker 定时分批删除 | 永久追加写、不可删除（初版假设） | 按月分区，到期 `DROP PARTITION` |

B/C 的共同代价：外部 SDK 会把还没有需求的失败模式（回调重放、限流、密钥轮换）提前绑进事务边界；只读副本会引入复制延迟下的「刚结账查不到」；自动清分需要定义债权归属、结算周期与差错处理；永久保留审计日志与「只保留 30 天」直接冲突；按月分区会与「暂不分区」（ADR-0004）以及复合唯一 / 外键设计冲突，且当前删除量用索引 + 分批 `DELETE` 足够。

## 决策

### 1. OQ-03：R1 不接外部服务，保留适配器接口

1. R1 不接入支付网关、短信、对象存储或任何第三方 SDK；Outbox 在 R1 的订阅者全部是**进程内**订阅者（预聚合、报表物化），没有外部投递目标。
2. `usecase/port/` 定义网关接口、`adapter/gateway/` 保留目录位置，但**不放具体 SDK 实现**；打印适配器明确排除（ADR-0004）。
3. 未来接入任何外部服务时另立 ADR，评估回调幂等、密钥管理、超时与重试、Outbox 投递语义；不得靠「先加个 SDK 试试」渐进引入。

### 2. OQ-04：前端框架由 `porch-console` 独立决策

1. 后端只保证 **REST + OpenAPI** 契约，不绑定框架、不提供框架专属 SDK、不做 BFF。
2. 前端框架、API 客户端生成方式、状态管理、组件库与 E2E 工具由 `porch-console` 自行决定并单独记录；`design/03` 的接口契约不受影响。
3. **本条关闭的是「归属问题」，不是「选型问题」**；具体框架仍列在「仍需确认」，但不阻塞后端 R1。

### 3. OQ-05：支持编排平台，暂不读写分离

1. **进程无状态**：`cmd/api` 与 `cmd/worker` 可水平扩缩；当前门店在客户端持有（ADR-0006）、权限每次请求实时推导（ADR-0002 阻断项 ⑧），因此任何副本都能处理任何请求，不需要会话粘滞。
2. **单主库读写**：所有读写走同一个 PostgreSQL 18.7 主库；**不引入只读副本、读写分离代理或最终一致的读路径**。重报表继续靠 L2 预聚合（`design/05` 第 8 节）与流式导出（L3）扛住。
3. **配置与密钥**：全部从环境变量 / 平台 Secret 注入，启动即校验；镜像保持多阶段构建到 `distroless/static`、非 root 运行（ADR-0002）。`/health` 与 `/ready` 分别用于存活与就绪，优雅停机停止接新请求并等待在途任务超时上限。
4. **迁移只跑一次**：迁移由独立的发布步骤 / 一次性 Job 执行，**禁止每个 Pod 启动时各自跑迁移或隐式建表**（承接 `design/02` 第 6 节）；`/ready` 校验迁移版本符合预期，版本不符的实例不接流量。
5. **定时任务多副本防重**：worker 的调度继续用 PG advisory lock（`design/05` 第 7 节），保证同一执行键在任意副本数下只跑一次；扩缩副本不改变任务语义。
6. **连接池预算**：`max_conns` 按「`api` 副本数 × 每实例上限 + `worker` 副本数 × 每实例上限 + 运维预留 ≤ PG `max_connections`」推导并显式配置，禁止沿用驱动默认值（`design/05` 第 10 节）。
7. **本地 `docker-compose.yml` 只用于开发**，不是生产部署形态；生产清单的具体平台与形态仍待确认（见下节）。支持编排平台不意味着 R0 就要产出部署清单。

### 4. OQ-07：不做跨店自动清分

1. 跨店会员消费按「消费发生在哪家店」记录，`shop_id` 仍是唯一归属维度；不引入内部往来账、结算单、债权表或定期清分任务。
2. 跨店核销仍是一次**显式业务动作**（`design/06` F-03）：两家店各写一条流水、用同一个 `transfer_ref` 关联，不修改会员档案归属、不提权、不生成清分结果。
3. 因差额产生的经营分析需求，用按店分组的报表呈现，不自动改写任何账务数据。将来确需清分时另立 ADR 并定义结算周期、差错处理与历史数据口径。

### 5. OQ-08：审计日志默认保留 30 天，可配置，定时删除

1. **分类**：`audit_logs` 是基础设施 / 运行期数据表（P 类），**不是业务数据**。它不受 ADR-0004「业务数据在线全量保留」约束，因此定时清理不违反「暂不归档」。
2. **保留窗口**：默认 **30 天**，可配置（配置项 `AUDIT_LOG_RETENTION_DAYS`，全局生效、启动时校验）；按 `created_at` 与 UTC+8 日界计算截止点。配置粒度、取值范围、是否允许超过 30 天、是否允许关闭清理，列入「仍需确认」。
3. **不可变语义修订**：审计记录对**所有业务请求**仍是只追加、不可更新、不可删除；**唯一允许的删除**是 worker 的定时清理任务，按批 `DELETE ... WHERE created_at < cutoff`，分批提交、可重入、失败重试并告警。业务代码不得暴露任何按 ID 删除 / 修改审计记录的端点或直接 SQL。
4. **不做归档、不分区**：超期记录物理删除，不导出归档、不提供「归档审计查询」、不建月度分区；用 `(created_at)` 索引 + 分批删除 + 表膨胀监控（`VACUUM` 策略在 R1 实现时定）控制代价。
5. **可查范围**：窗口内可检索与导出；窗口外查询必须返回明确的「超出保留期」语义，不能伪装成空结果或静默少数据。具体错误码与文案在 `design/03` 契约中定。
6. **清理动作自身可观测**：记录结构化日志与指标（删除行数、耗时、当前保留天数、失败次数），**不写回 `audit_logs`**（否则清理会不断产生新日志，形成自我循环）。
7. **三组边界**：「审计日志定时删除 ≠ 业务数据归档」「运行期清理 ≠ 业务单据删除」「业务请求不可删审计 ≠ 清理任务不可删」。

## 理由

1. **把最后一批默认假设变成决策**：OQ 全部关闭后，详细设计只剩 DP-01–07 的评审与实现级细节，冻结条件清晰；贡献者不再按各自理解脑补部署形态或审计留存。
2. **编排平台与模块化单体并不矛盾**：无状态进程 + 单主库既支持水平扩缩，又保留单库事务强一致，不需要为多副本牺牲隔离正确性或幂等语义。暂不读写分离让「刚写完立刻查得到」继续成立，报表压力由既有的预聚合与流式导出承担。
3. **审计日志 30 天是可控的成本取舍**：只追加日志是增长最快、查询频次最低的表，定时清理能直接压住库体积；把它明确归类为运行期数据，既满足保留要求，又不给业务数据开「保留窗口」这个口子。
4. **不做自动清分保住单店核算**：一旦引入门店间债权，报表就要同时回答「谁卖了」和「谁该收钱」，与「一条业务记录只属于一个 `shop_id`」（ADR-0003）冲突。

## 后果与限制

- **修订 ADR-0004 第 3 节第 3 条**：运行期清理清单从「幂等键 / 已投递事件 / 导出临时文件」扩展为**再加 `audit_logs` 超期记录**；「业务单据与流水不参与清理」不变。ADR-0004 第 74 行「其余开放问题继续待确认」由本文取代。
- `design/02` 第 7 节里「审计日志不设保留年限」、`design/05` 第 11 节里「不可更新删除」等表述一并订正；`design/04` 的 gateway 注释、进程与评审清单，`design/06` 的跨店核销与报表前提同步。
- 支持编排平台带来的新约束（迁移只跑一次、定时任务防重、连接池预算、探针与优雅停机）进入 `design/04`、`05` 与 PR 自查；R0 仍只提供本地 Compose 开发库，不产出生产清单。
- 将来要接外部服务、引入读写分离 / 只读副本、做跨店清分、延长审计留存或满足长期合规举证，均属**范围扩展或部署架构变更**，须新建 ADR；延长审计留存尤其要注意已删除数据不可恢复。
- `design/00` 第 8 节的 **OQ-01 至 OQ-08 全部关闭**；7 项设计提案 DP-01–07 仍需评审，整套详细设计**仍是提案、尚未冻结**。

## 仍需确认（本文新引入或承接的未决项）

完整清单与优先级见 [`../design/00-overview.md`](../design/00-overview.md) 第 8.2 节，此处只列摘要：

1. **DP-01–07 七项设计提案**是否逐项接受（尤其 DP-01「不拆微服务」与本文「支持编排平台」需一起确认）。
2. **ADR-0006 悬置假设**：「一人多店」是主体视角 1:N + `user_shops` 多对多（当前实现），还是严格 1:N 的 `users.shop_id` 外键。
3. **编排平台的具体形态**：Kubernetes / Nomad / 云容器服务等；配置与密钥注入、Ingress 与 TLS 终止、滚动发布与停机时长、副本数上限。
4. **迁移执行方式与连接池预算的具体数值**（发布流水线 / Job、每实例 `max_conns`、PG `max_connections` 预留）。
5. **审计保留配置细节**：取值范围、是否允许 > 30 天或关闭清理、是否可按店覆盖、变更是否需重启、按 UTC+8 自然日还是滚动时长、批量大小与 `VACUUM` 策略。
6. **审计查询超期的契约**：错误码与文案、窗口内导出是否单独提供。
7. **前端具体框架选型**（`porch-console` 独立决定，不阻塞后端）。
8. **R2+ 外部集成清单与时点**、**未来是否需要跨店清分**、**详细设计冻结与 R1 范围**、**容量与告警阈值**。

## 复审条件

- 引入只读副本、读写分离或跨区域部署；
- 审计日志被要求满足法定留存年限、举证或不可删改要求；
- 出现跨店结算 / 加盟分账的真实需求；
- 接入任何外部支付、短信或对象存储服务；
- 编排平台形态确定且需要产出部署清单，或 DP-01 被修订；
- 上游 ADR-0002 / 0003 / 0004 / 0006 任一被修订且影响本文口径。
