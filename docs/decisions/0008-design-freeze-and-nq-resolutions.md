## 背景

[ADR-0007](0007-remaining-open-questions.md) 关闭了 OQ-01–08，但把实现级细节留成 NQ-01–16，并明确「NQ-01/02/03 不答，详细设计不能冻结、R1 不能开工；NQ-06/07 不答，编排平台上线会出事故」。本轮用户逐项作答，其中三类答复需要额外处理：

1. **直接确认类**（NQ-01/02/03/04）：落决议即可；NQ-02 明确为**多对多**，因此 ADR-0006 的悬置假设关闭、schema 与切换协议不变。
2. **收紧既有口径类**（NQ-05/06/07/08/09）：ADR-0007 写的是「支持编排平台」这一**架构能力**，本轮给出的是**当前落地形态**——Docker 多副本、Go 编写的 Job、副本数 2。二者是「能力约束」与「本期实现」的关系，不是推翻。
3. **要建议 / 要例子 / 要详细说明类**（NQ-08/11/12/13/16）：其中 NQ-11 把「按 UTC+8 自然日还是滚动 30×24h」原样抛回，需要由后端选一个并给出理由；NQ-12 要错误码建议；NQ-16 要跨店差额的详细说明。这三项由本文给出结论，展开写在新增分册里。

此时业务代码尚未开始，schema 与接口仍是设计提案，固定口径没有历史数据迁移成本。

### 理解澄清（本轮最容易被误读的四处）

| 说法 | 准确含义 |
|---|---|
| 「NQ-02 多对多」 | 确认 ADR-0006 当前口径：**主体视角一人多店（1:N）+ 关系实现 `user_shops` 多对多**。不是改成 `users.shop_id` 外键，也不新增「店主账号」层级；ADR-0006 全文条款不变 |
| 「目前由 docker 部署，副本数为 2」 | 当前落地平台是 Docker（`api` × 2 / `worker` × 2），**不产出 Kubernetes / Nomad / 云容器服务清单**。ADR-0007 的「进程无状态、可水平扩缩、迁移只跑一次、定时任务加锁、连接池按副本推导」继续有效，且因为副本数确定而可以给出具体数值 |
| 「job 使用数据库方式共享」 | 一次性任务与定时任务都是 **Go 进程 `cmd/job` / `cmd/worker`**；跨副本的共享状态、互斥与运行记录**全部在 PostgreSQL**（goose 版本表、advisory lock、运行记录表、Outbox / 幂等 / 导出任务表）。不引入平台 Job、外部调度服务、Redis 协调、共享文件系统或「按副本编号分片」 |
| 「NQ-16 需要详细说明」 | 按「**维持 ADR-0007 第 4 节不做自动清分**，补充跨店差额的口径、报表呈现与未来启用条件」执行，详见 [`../design/09-cross-shop-difference.md`](../design/09-cross-shop-difference.md)。若本意是**启用**自动清分，属范围变更，须另立 ADR 并推翻 ADR-0007 第 4 节，不能用「补充说明」渐进引入 |

## 备选方案

| 议题 | 方案 A（采用） | 方案 B | 不选 B 的原因 |
|---|---|---|---|
| DP-01 与部署 | 模块化单体 + 无状态多副本（2+2） | 拆微服务以配合水平扩缩 | 单库事务与「一条业务记录只属于一个 `shop_id`」会被拆散，隔离正确性成本远高于收益 |
| 审计清理窗口 | **UTC+8 自然日**（最近 30 个完整自然日 + 当日） | 滚动 30×24h | 滚动窗口每次任务的 cutoff 都不同，无法向使用者解释「最早可查哪天」，也无法稳定复现测试；且与 ADR-0004 的业务日 / 单号日期口径不一致 |
| 超期查询语义 | `400 AUDIT_RETENTION_WINDOW_EXCEEDED` + 可查下界 | 返回空列表 / `404` / `410` | 空列表会让前端把「超期」渲染成「没有数据」；404/410 描述的是资源不存在，而这里是**范围参数越界**，客户端可修正 |
| 审计导出 | 复用统一导出任务，不单开专用端点 | 新增 `/audit-logs/export` | 两套分页 / 权限 / 限流 / 窗口校验实现，且 R1 首批不含审计查询界面 |
| 一次性任务 | Go `cmd/job` + PG advisory lock + 版本表 | 平台 Job / CronJob / shell 编排 | 会把互斥与版本判断分散到平台配置，本地 Docker 与未来平台行为不一致；`cmd/job` 复用同一套 Go 配置、日志与 SQL |
| 多副本防重 | 每个执行键一把 PG advisory lock | 按副本索引分片任务 | 扩缩容后分片映射立刻失效，且「同一任务任意副本数下只跑一次」变成依赖部署拓扑 |

### 2. 详细设计冻结

1. **冻结对象**：`docs/design/00`–`09` 全册、[`docs/ARCHITECTURE.md`](../ARCHITECTURE.md) 原则层、ADR-0001–0008。设计状态由「提案」改为 **Frozen（2026-11-15）**；DP-01–07 作为已接受决策写入 `design/00` 第 7 节。
2. **冻结的含义**：schema 形状与唯一性范围、`shop_id` 隔离条件、状态机、错误码与 `retryable` 语义、分层与依赖方向、端点清单与响应形状、门店上下文协议、以及本文固定的副本数 / 连接池 / 保留天数 / 清理窗口口径，都属于**先改设计再改代码**：任何 PR 改动其中之一，必须同时更新对应分册（或新 ADR），并在 PR 描述里指出影响章节。只改实现、不改契约的 PR 不需要改设计文档。
3. **冻结不意味着不再演进**：新增业务域、性能校准、部署平台替换都允许，但走「ADR / 设计变更 + 文档同步」，不在代码里悄悄引入第二套口径。
4. **状态同步**：`design/00` 第 8.2 节由「NQ 待确认清单」改为「NQ 已决议清单」；ADR-0006 的悬置假设、ADR-0007 的「仍需确认」与「详细设计尚未冻结」表述一并订正。

### 3. R1 首批端点范围与验收标准

**范围**（与 README 路线图 R1「领域模型 + `shop_id` 单层隔离 + 单店 CRUD + 集成测试基线」一致）：

| 纳入 R1 首批 | 不纳入 R1 首批（契约已冻结，实现按路线图 R2/R3） |

| `GET/POST /shops`、`GET/PATCH /shops/{shopId}`、`GET/PATCH /shops/{shopId}/settings` | 库存余额、出入库、跨店调拨（R2/R3） |
| `GET/POST /catalog-items`、`GET/PATCH /catalog-items/{id}`、`GET /catalog-categories`、`GET/PUT /shops/{shopId}/catalog-overrides/{itemId}` | 报表、跨店汇总、导出任务（R2/R3） |
| `GET/POST /members`、`GET/PATCH /members/{id}`、`GET /shops/{shopId}/members/{id}/balance`、`/ledger` | 审计查询界面、WebSocket、外部集成回调 |

| 所有写操作统一带 `Idempotency-Key`；所有单店请求统一带 `X-Shop-Id` | — |

**验收标准**（R1 完成的定义）：

1. `design/00` 第 2 节质量属性 **1–5、7、9** 全部有集成测试佐证；第 6（内存稳定性）与第 8（读性能）由 **2 副本压测报告**给出实测值。
2. 契约冻结（DP-06）：`api/openapi.yaml` 由注释生成，CI 校验「重新生成后无 diff」；响应快照测试只断言字段集合与类型。
3. 集成测试覆盖：迁移 `up → down → up`、并发单号唯一、复合外键拒绝跨店明细、隔离越权、幂等重放、`user_shops` 双向查询、UTC+8 日界（UTC 16:00）前后业务日归属、审计清理「只删超期行、不碰业务单据」。
4. **2+2 部署基线**：`cmd/job migrate` 只执行一次且 `api` / `worker` 启动均不跑迁移；`/ready` 在版本不符时返回 503；定时任务在两个 worker 副本下只产生一条 `succeeded` 运行记录；连接池实际水位 ≤ 本文预算。
5. **审计清理**：按 UTC+8 自然日 cutoff 删除，`audit_log_cleanup_runs` 有成功记录与指标，超期查询返回本文冻结的错误码而不是空列表。

### 4. 本次新增的可执行基线（摘要）

| 主题 | 基线 | 详见 |
|---|---|---|

| 一次性任务 | Go `cmd/job`；发布顺序 `job migrate` → 起 `api`/`worker`；进程启动不跑迁移 | `design/07` §3 |

| 容量告警 | 库体积 / 表体积 / `Seq Scan` / 慢查询 / 连接池水位 / 死元组，数值见分册 | `design/07` §5 |
| 审计保留 | 默认 30 天（1..3650），UTC+8 自然日窗口，每日 03:30，单批 5000 行 | `design/08` §1–§3 |

## 理由

1. **冻结条件由用户明确给出**：NQ-03 的答复是「完成目前待确认项即冻结」，本轮 16 项全部有结论，冻结不再缺前置。把 R1 范围与验收标准同时写死，避免冻结后靠口头理解决定开工边界。
2. **把「能力」与「本期实现」分开**：ADR-0007 只要求无状态可扩缩，本轮把它落到 Docker 2+2 与具体数值，既让压测与连接池预算可算，又不放弃未来换平台的可能。
3. **共享状态只有一处**：Job 用 Go、协调用数据库，本地 Docker 与任何未来编排平台的行为一致；平台差异只影响「谁拉起容器」，不影响「谁跑迁移、谁抢到锁」。
4. **自然日窗口可解释、可复现**：审计保留期要能被使用者和客服说清楚（「最早可查 10 月 16 日」），也要能在集成测试里用固定时间点断言；滚动窗口做不到这两点。
5. **超期要明确报错**：审计日志是唯一会被物理删除的表，若查询超期返回空列表，前端必然渲染成「没有操作记录」，这是不报错的错数据，与 `design/00` 质量属性第 1 条同类。

## 后果与限制

- **修订 [ADR-0006](0006-user-shops-and-current-shop.md)**：「后果与限制」中的「待确认：严格 1:N 假设」改为**已确认 `user_shops` 多对多**；其余条款（含「一人多店 ≠ 一店一人」）不变，schema 与切换协议零改动。
- **修订 [ADR-0007](0007-remaining-open-questions.md)**：「仍需确认」一节全部关闭；「后果与限制」中「7 项设计提案仍需评审，整套详细设计仍是提案、尚未冻结」改为「已由 ADR-0008 接受并冻结」。第 3 节「支持编排平台」的**能力约束不变**，但本期落地平台收敛为 Docker 2+2；第 5 节审计保留的「取值上限、批量大小、VACUUM 策略」等口径由 `design/08` 定稿。
- **修订 ADR-0004 的关联表述**：审计清理仍属运行期清理、不构成业务归档；但其窗口口径、运行记录表与错误契约现在固定，不再是「实现时再定」。
- 新增三册 `design/07`–`09`；`design/00`–`06` 的 NQ 引用、「提案 / 尚未冻结」状态、连接池与审计细则引用同步替换；README、CHANGELOG、LOCAL-DEV、`.env.example`、`porch-console` README 同步。
- `audit_log_cleanup_runs` 是 P 类基础设施表，**不带 `shop_id`、不参与业务隔离判定、不是审计记录**；每日最多数行，不设自动清理。
- NQ-09 的配置注入 / TLS / 滚动发布时长、NQ-14 的具体框架名、NQ-15 的集成时点、NQ-16 的未来清分条件，属于**已登记的延后项**，不是未答问题；改变它们各自需要新 ADR 或前端仓决策记录。
- **公开仓库脱钩约束不变**：NQ-14 涉及的既有内部前端工程名称、源码与任何内部项目标识不得出现在两个公开仓库；该信息只在本地项目管理资料中保留。

## 已无待确认项

NQ-01–16、OQ-01–08、DP-01–07 **全部关闭**。后续出现的任何新问题使用新的编号体系并单独记录，不复用 OQ / NQ 编号、不重新打开本清单。

## 复审条件

- 部署平台从 Docker 换成 Kubernetes / Nomad / 云容器服务，或副本数不再是 2+2（连接池预算与压测基线必须重算）；
- 需要接入任何外部服务、引入只读副本或读写分离、拆微服务、启用跨店自动清分；
- 审计日志被要求满足法定留存年限、举证或不可删改要求，或保留天数超出 `1..3650`；
- `AUDIT_LOG_RETENTION_DAYS` 被要求按店覆盖、热加载或关闭清理；
- 容量指标达到 `design/07` §5 的阈值，需要评估分区 / 归档；
- 上游 ADR-0001–0007 任一被修订且影响本文口径。
