# 前期系统架构详细设计 · 00 总览

> **状态：设计提案，尚未冻结。** 本册与 `01`–`06` 共同构成 R1（业务代码开工）之前的详细设计基线。
> **上游约束**：[ADR-0001](../decisions/0001-postgresql-18.md)（PostgreSQL 18.7）、[ADR-0002](../decisions/0002-go-backend-stack.md)（Go + SQL 优先）、[ADR-0003](../decisions/0003-shop-level-isolation.md)（数据隔离只有 `shop_id` 一层）、[ADR-0004](../decisions/0004-scope-baseline.md)（单币种 / 东八区 / 暂不归档 / 不打印 / 不离线）、[ADR-0005](../decisions/0005-no-shop-groups.md)（取消门店组，跨店改用显式门店集合）、[ADR-0006](../decisions/0006-user-shops-and-current-shop.md)（用户可拥有多店、当前门店可切换）。本套文档只展开「怎么实现」，不新增与六者冲突的决策；[架构原则](../ARCHITECTURE.md) 仍是原则层的权威。

## 1. 目的与范围

| | 内容 |
|---|---|
| 本套文档回答 | 系统分成哪些模块、数据怎么落库、接口长什么样、代码放在哪、一次结账怎么走、横切机制怎么保证正确性 |
| 不回答 | 具体框架源码写法、第三方 SDK 选型、部署脚本、UI 交互、行业专属业务规则 |
| 适用阶段 | R0 → R1 设计评审；R1 实现过程中若与设计不符，**先改设计再改代码** |
| 读者 | 后端贡献者、代码评审者、`porch-console` 的接口对接方 |

前期设计的价值在于把「一旦写错就要返工的地基」先固定：schema、唯一性范围、事务边界、隔离条件的注入位置、错误语义。这些在代码写完后改，成本会成倍上升。

## 2. 质量属性与可验收目标

优先级从上到下；冲突时**上面的压倒下面的**（例如为了隔离正确性，可以牺牲一点查询便利性）。

| 序 | 属性 | 可验收目标 | 验证方式 |
|---|---|---|---|
| 1 | 数据隔离正确性 | 任何请求都不会读到其可见门店集合之外的数据，切换门店后也不残留上一家店的数据 | 每个查询类 PR 检查 SQL 中显式 `shop_id`；集成测试覆盖「同主体跨店越权」「报表跨店聚合」与「门店切换 + 在途请求」（F-07，ADR-0006） |
| 2 | 账务正确性 | 金额、数量无浮点误差；已支付单据不可被静默改写 | CI 扫描金额路径禁用 `float64`；计价纯函数表驱动测试；账单不可变约束由数据库与状态机双重保证 |
| 3 | 写入幂等 | 所有产生副作用的写操作在重放、重试、回调重复时不重复记账 | 集成测试对每个写用例重放两次，断言只有一次副作用 |
| 4 | 单号唯一 | 并发下单号不重复，且不依赖应用层拼接 | `(shop_id, order_no)` 唯一约束 + 并发压测 |
| 5 | 权限即时性 | 授权变更后下一个请求即生效 | 集成测试「改授权 → 立即请求 → 断言结果变化」，禁止缓存判定 |
| 6 | 内存稳定性 | 报表导出常驻内存不随结果集线性增长 | 大结果集导出压测，观察 RSS 曲线 |
| 7 | 可演进性 | 新增业务域不修改核心表、不改动既有查询的隔离条件 | 模块边界 lint（`depguard`）+ 扩展点约定（见 `01` 第 8 节） |
| 8 | 读性能 | 单店常用列表 p95 < 200 ms（10 万行单据量级）；跨店日报 < 2 s | 压测 + `EXPLAIN (ANALYZE, BUFFERS)` 存档 |
| 9 | 可运维性 | 启动即校验配置、健康检查、优雅停机、结构化日志贯穿 request id | 集成测试 + 上线清单 |

> 性能目标排在第 8 位不是疏忽：这类系统最贵的事故是「A 店的数据出现在 B 店的页面上」，它不报错、不告警，只能靠设计阶段防住。

## 3. 系统上下文

```
                    ┌──────────────────────┐
                    │  经营者 / 店员 / 管理员 │
                    └──────────┬───────────┘
                               │ HTTPS
                    ┌──────────▼───────────┐
                    │   porch-console      │  前端控制台（框架待定）
                    │   全局门店上下文      │
                    └──────────┬───────────┘
                               │ REST + OpenAPI（JSON）
        ┌──────────────────────▼──────────────────────┐
        │              porch-os  API 进程              │
        │  认证 → 权限 → shop scope → 幂等 → 用例 → SQL │
        └───────┬──────────────────────────┬──────────┘
                │                          │
        ┌───────▼────────┐        ┌────────▼─────────┐
        │ PostgreSQL 18.7│        │  porch-os worker │
        │ 单库 / 单 schema│◄───────│ 预聚合 / Outbox  │
        └───────┬────────┘        │ 定时任务 / 导出   │
                │                 └────────┬─────────┘
        ┌───────▼────────┐                 │
        │ Redis（可选 R2）│◄────────────────┘
        │ 缓存 / 幂等 / 锁│
        └────────────────┘
```

- **单库单 schema**：所有门店共用一套表，靠 `shop_id` 区分，不存在上层维度。
- **两个进程**：`api` 处理在线请求，`worker` 处理预聚合、事件派发、导出与定时任务；两者共用同一份迁移与领域代码，但各自可独立扩缩。
- **Redis 从 R2 引入**：R1 的幂等、Outbox、分布式锁先落库实现，避免一开始就依赖外部组件；接口保持不变，后续替换实现。

## 4. 模块划分

模块化单体，按业务边界分包；**模块之间不直接查对方的表**，只通过用例层编排与 ID 引用。

| 模块 | 职责 | 主要聚合 / 实体 | 数据归属 |
|---|---|---|---|
| `identity` | 用户、角色、权限、可见门店集合、令牌、审计 | `User` / `Role` / `Permission` | 全局主数据 + 授权关系 |
| `shop` | 门店、门店设置、营业日；不设门店组（ADR-0005） | `Shop` | 全局主数据 |
| `catalog` | 商品与服务目录、分类、按店价格与上下架覆盖 | `CatalogItem` / `ShopCatalogOverride` | 全局主数据 + 门店覆盖 |
| `member` | 会员档案（全局唯一）、按店余额与流水 | `Member` / `MemberBalance` / `BalanceLedger` | 全局档案 + 门店账 |
| `order` | 单据、明细、支付、退款、收银班次 | `Order` / `Payment` / `Refund` / `Shift` | 门店业务数据 |
| `inventory` | 按店库存、出入库流水、跨店调拨 | `InventoryBalance` / `StockMovement` | 门店业务数据 |
| `reporting` | 实时查询、日汇总预聚合、导出任务 | `DailyShopSummary` / `ExportJob` | 派生数据（可重算） |
| `platform` | 幂等键、Outbox、错误分类、配置、事务、可观测性 | `IdempotencyKey` / `OutboxEvent` | 基础设施 |

模块依赖方向：`order` / `reporting` 可编排 `catalog` / `member` / `inventory`；反向依赖禁止；`platform` 被所有模块依赖但自身不依赖任何业务模块。

## 5. 数据归属三分法（承接 ADR-0003）

这是整套设计最容易写错的地方，先给唯一口径：

| 类别 | 是否带 `shop_id` | 例子 | 规则 |
|---|---|---|---|
| **A. 全局主数据** | 不带 | `shops`、`users`、`roles`、`catalog_items`、`members` | 全局唯一；`shops.id` 本身就是 `shop_id`，不自引用，也不带分组 / 层级列（ADR-0005） |
| **B. 门店业务数据** | **必带，且为复合索引前导列** | `orders`、`order_lines`、`payments`、`inventory_balances`、`member_balances`、各类流水 | 一条记录只属于一家店；跨店查看是查询时的聚合，不是写入时的归属 |
| **C. 授权 / 关系数据** | 含 `shop_id` 列，但语义是关系而非隔离维度 | `user_shops`（唯一来源） | 用于推导「可见门店集合」；不参与业务表的归属判定；不存在分组关系表 |

> C 类表含 `shop_id` 不构成第二层隔离维度：它描述的是用户与门店之间的关系，不是把数据挂到某个上层实体。ADR-0003 禁止的是 tenant / org / company 这类**上层归属**，不是禁止出现 `shop_id` 这一列；ADR-0005 进一步取消门店组，可见门店集合是请求期推导结果，不是可持久化的对象。
>
> 另有一类**平台基础设施表**（幂等键、Outbox、审计、导出任务）不属于 A/B/C，不参与业务归属判定。其中审计日志里与门店相关的记录仍带 `shop_id` 以便按店检索，账号级操作该列为 `NULL`——这不是隔离维度的例外，因为它不是业务表。

跨店共享实体（会员档案、商品目录）全局唯一；其**产生业务副作用的数据**（余额、流水、库存、单据）一律归入 B 类。跨店核销是显式业务动作，不提升任何数据权限。

## 6. 分层与进程

```
cmd/api        → 只做装配与启动
cmd/worker     → 只做装配与启动
internal/
  domain/      → 纯业务：值对象、状态机、计价、折叠函数（零外部依赖）
  usecase/     → 用例编排：事务边界、权限校验、跨模块协作
  adapter/
    http/      → 路由、中间件、DTO 转换
    postgres/  → sqlc 静态 SQL、squirrel 动态筛选、扁平 DTO、迁移
    redis/     → 缓存与锁（R2 起）
  platform/    → 配置、日志、UoW、错误、指标、追踪
  di/          → wire 装配
```

依赖单向向下：`domain` 不得 import `adapter` / `platform`；`usecase` 只依赖 `domain` 与接口；`adapter` 实现接口。由 lint 规则强制，详见 `04`。

## 8. 开放问题（需确认后才进入实现）

### 8.1 已确认决议（ADR-0004 / 0005 / 0006，2026-11-15）

以下四项开放问题已由 [ADR-0004](../decisions/0004-scope-baseline.md) 冻结，**不再是开放问题**；另有一条设计初版的**内置假设**（门店组）不是开放问题，由 [ADR-0005](../decisions/0005-no-shop-groups.md) 明确取消；用户与门店的关系基数、当前门店切换协议则由 [ADR-0006](../decisions/0006-user-shops-and-current-shop.md) 明确。本文各分册按这三份 ADR 的口径描述。

| 编号 | 原问题 / 假设 | 已确认结论 | 落地位置 |
|---|---|---|---|
| OQ-01 | 是否支持多币种 / 多时区门店？ | **单币种 CNY（¥）**，金额列与 `Money` 不带币种；**统一东八区 `Asia/Shanghai`**，无门店级时区、无客户端时区参数。存储仍 `timestamptz` UTC，展示/业务日/单号日期按 UTC+8 | `01` §4/§6、`02` §1/§3、`03` §1/§5、`05` §8 |
| OQ-02 | 日报/流水的保留年限与归档方式？ | **暂不归档**：在线全量保留业务数据，不设保留窗口、不分区、不提供归档查询；仅清理幂等键、已投递事件、导出临时文件等运行期数据 | `02` §7、`05` §6/§8 |
| OQ-03（打印部分） | 打印是否进 R1？ | **不支持打印**：无打印端点、模板与设备适配；导出（Excel/CSV 下载）不受影响 | `03` §1、`04` §1、`05` §8 |
| OQ-06 | 是否需要断网可用的离线收银？ | **不需要**：全程在线强一致，不做本地队列、补传与冲突合并；网络失败只提示、不放行提交 | `05` §4.1、`06` §0 |
| ADR-0005 | 初版假设：需要门店组 / 店群做汇总与授权 | **不需要**：不设分组实体、分组表、分组端点与按组授权；跨店汇总 / 对比 / 导出能力保留，范围改由「可见门店集合 + 显式 `shop_ids`」表达；`user_shops` 仍是唯一授权来源 | `00` §4/§5、`01` §2/§3、`02` §2、`03` §3/§8、`05` §1/§8 |
| ADR-0006 | 初版未定义：用户与门店的关系基数、「当前门店」是什么 | **一个用户可拥有多间门店，可在页面切换**：从主体视角 1:N，关系实现仍是 `user_shops` 多对多（一店也可多人）；禁止 `users.shop_id` / `shops.owner_user_id`；当前门店是请求期上下文，不落表、不进 JWT、不作授权来源；单店请求必须显式带 `X-Shop-Id`；切换零写入、无服务端端点 | `01` §2/§6、`02` §2/§3/§8、`03` §3/§7、`04` §4、`05` §1/§5、`06` F-07 |

> 「运行期清理 ≠ 业务归档」「离线提示 ≠ 离线收银」「文件导出 ≠ 打印」三组边界由 ADR-0004 明确；**「取消门店组 ≠ 取消跨店汇总」**由 ADR-0005 明确；**「一人多店 ≠ 一店一人」「当前门店 ≠ 授权来源」「页面切换 ≠ 跨店汇总」**由 ADR-0006 明确，评审时不得混用。
