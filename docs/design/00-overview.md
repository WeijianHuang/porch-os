> **状态：设计提案，尚未冻结。** 本册与 `01`–`06` 共同构成 R1（业务代码开工）之前的详细设计基线。

## 1. 目的与范围

| | 内容 |
|---|---|
| 本套文档回答 | 系统分成哪些模块、数据怎么落库、接口长什么样、代码放在哪、一次结账怎么走、横切机制怎么保证正确性 |
| 不回答 | 具体框架源码写法、第三方 SDK 选型、部署脚本、UI 交互、行业专属业务规则 |
| 适用阶段 | R0 → R1 设计评审；R1 实现过程中若与设计不符，**先改设计再改代码** |
| 读者 | 后端贡献者、代码评审者、`porch-console` 的接口对接方 |

前期设计的价值在于把「一旦写错就要返工的地基」先固定：schema、唯一性范围、事务边界、隔离条件的注入位置、错误语义。这些在代码写完后改，成本会成倍上升。

## 2. 质量属性与可验收目标

优先级从上到下；冲突时**上面的压倒下面的**（例如为了隔离正确性，可以牺牲一点查询便利性）。

| 序 | 属性 | 可验收目标 | 验证方式 |
|---|---|---|---|
| 1 | 数据隔离正确性 | 任何请求都不会读到其可见门店集合之外的数据，切换门店后也不残留上一家店的数据 | 每个查询类 PR 检查 SQL 中显式 `shop_id`；集成测试覆盖「同主体跨店越权」「报表跨店聚合」与「门店切换 + 在途请求」（F-07，ADR-0006） |
| 2 | 账务正确性 | 金额、数量无浮点误差；已支付单据不可被静默改写 | CI 扫描金额路径禁用 `float64`；计价纯函数表驱动测试；账单不可变约束由数据库与状态机双重保证 |
| 3 | 写入幂等 | 所有产生副作用的写操作在重放、重试、回调重复时不重复记账 | 集成测试对每个写用例重放两次，断言只有一次副作用 |
| 4 | 单号唯一 | 并发下单号不重复，且不依赖应用层拼接 | `(shop_id, order_no)` 唯一约束 + 并发压测 |
| 5 | 权限即时性 | 授权变更后下一个请求即生效 | 集成测试「改授权 → 立即请求 → 断言结果变化」，禁止缓存判定 |
| 6 | 内存稳定性 | 报表导出常驻内存不随结果集线性增长 | 大结果集导出压测，观察 RSS 曲线 |
| 7 | 可演进性 | 新增业务域不修改核心表、不改动既有查询的隔离条件 | 模块边界 lint（`depguard`）+ 扩展点约定（见 `01` 第 8 节） |
| 8 | 读性能 | 单店常用列表 p95 < 200 ms（10 万行单据量级）；跨店日报 < 2 s | 压测 + `EXPLAIN (ANALYZE, BUFFERS)` 存档 |
| 9 | 可运维性 | 启动即校验配置、健康检查、优雅停机、结构化日志贯穿 request id | 集成测试 + 上线清单 |

> 性能目标排在第 8 位不是疏忽：这类系统最贵的事故是「A 店的数据出现在 B 店的页面上」，它不报错、不告警，只能靠设计阶段防住。

## 3. 系统上下文

```
                    ┌──────────────────────┐
                    │  经营者 / 店员 / 管理员 │
                    └──────────┬───────────┘
                               │ HTTPS
                    ┌──────────▼───────────┐
                    │   porch-console      │  前端控制台（框架由该仓独立决策）
                    │   全局门店上下文      │
                    └──────────┬───────────┘
                               │ REST + OpenAPI（JSON）
        ┌──────────────────────▼──────────────────────┐
        │              porch-os  API 进程              │
        │  认证 → 权限 → shop scope → 幂等 → 用例 → SQL │
        └───────┬──────────────────────────┬──────────┘
                │                          │
        ┌───────▼────────┐        ┌────────▼─────────┐
        │ PostgreSQL 18.7│        │  porch-os worker │
        │ 单库 / 单 schema│◄───────│ 预聚合 / Outbox  │
        └───────┬────────┘        │ 定时任务 / 导出   │
                │                 └────────┬─────────┘
        ┌───────▼────────┐                 │
        │ Redis（可选 R2）│◄────────────────┘
        │ 缓存 / 幂等 / 锁│
        └────────────────┘
```

- **单库单 schema**：所有门店共用一套表，靠 `shop_id` 区分，不存在上层维度。
- **两个进程**：`api` 处理在线请求，`worker` 处理预聚合、事件派发、导出与定时任务；两者共用同一份迁移与领域代码，但各自可独立扩缩。
- **Redis 从 R2 引入**：R1 的幂等、Outbox、分布式锁先落库实现，避免一开始就依赖外部组件；接口保持不变，后续替换实现。
- **部署形态（ADR-0007）**：`api` / `worker` 无状态，支持编排平台水平扩缩；**单主库读写，暂不读写分离、不引入只读副本**。迁移由独立一次性任务执行（每个 Pod 不各自跑），定时任务靠数据库锁防重，连接池按副本数推导。本地 `docker-compose.yml` 仅用于开发，不是生产部署形态。

## 4. 模块划分

模块化单体，按业务边界分包；**模块之间不直接查对方的表**，只通过用例层编排与 ID 引用。

| 模块 | 职责 | 主要聚合 / 实体 | 数据归属 |
|---|---|---|---|
| `identity` | 用户、角色、权限、可见门店集合、令牌、审计 | `User` / `Role` / `Permission` | 全局主数据 + 授权关系 |
| `shop` | 门店、门店设置、营业日；不设门店组（ADR-0005） | `Shop` | 全局主数据 |
| `catalog` | 商品与服务目录、分类、按店价格与上下架覆盖 | `CatalogItem` / `ShopCatalogOverride` | 全局主数据 + 门店覆盖 |
| `member` | 会员档案（全局唯一）、按店余额与流水 | `Member` / `MemberBalance` / `BalanceLedger` | 全局档案 + 门店账 |
| `order` | 单据、明细、支付、退款、收银班次 | `Order` / `Payment` / `Refund` / `Shift` | 门店业务数据 |
| `inventory` | 按店库存、出入库流水、跨店调拨 | `InventoryBalance` / `StockMovement` | 门店业务数据 |
| `reporting` | 实时查询、日汇总预聚合、导出任务 | `DailyShopSummary` / `ExportJob` | 派生数据（可重算） |
| `platform` | 幂等键、Outbox、错误分类、配置、事务、可观测性 | `IdempotencyKey` / `OutboxEvent` | 基础设施 |

模块依赖方向：`order` / `reporting` 可编排 `catalog` / `member` / `inventory`；反向依赖禁止；`platform` 被所有模块依赖但自身不依赖任何业务模块。

## 5. 数据归属三分法（承接 ADR-0003）

这是整套设计最容易写错的地方，先给唯一口径：

| 类别 | 是否带 `shop_id` | 例子 | 规则 |
|---|---|---|---|
| **A. 全局主数据** | 不带 | `shops`、`users`、`roles`、`catalog_items`、`members` | 全局唯一；`shops.id` 本身就是 `shop_id`，不自引用，也不带分组 / 层级列（ADR-0005） |
| **B. 门店业务数据** | **必带，且为复合索引前导列** | `orders`、`order_lines`、`payments`、`inventory_balances`、`member_balances`、各类流水 | 一条记录只属于一家店；跨店查看是查询时的聚合，不是写入时的归属 |
| **C. 授权 / 关系数据** | 含 `shop_id` 列，但语义是关系而非隔离维度 | `user_shops`（唯一来源） | 用于推导「可见门店集合」；不参与业务表的归属判定；不存在分组关系表 |

> C 类表含 `shop_id` 不构成第二层隔离维度：它描述的是用户与门店之间的关系，不是把数据挂到某个上层实体。ADR-0003 禁止的是 tenant / org / company 这类**上层归属**，不是禁止出现 `shop_id` 这一列；ADR-0005 进一步取消门店组，可见门店集合是请求期推导结果，不是可持久化的对象。
>
> 另有一类**平台基础设施表**（幂等键、Outbox、审计、导出任务）不属于 A/B/C，不参与业务归属判定。其中审计日志里与门店相关的记录仍带 `shop_id` 以便按店检索，账号级操作该列为 `NULL`——这不是隔离维度的例外，因为它不是业务表。

跨店共享实体（会员档案、商品目录）全局唯一；其**产生业务副作用的数据**（余额、流水、库存、单据）一律归入 B 类。跨店核销是显式业务动作，不提升任何数据权限。

## 6. 分层与进程

```
cmd/api        → 只做装配与启动
cmd/worker     → 只做装配与启动
internal/
  domain/      → 纯业务：值对象、状态机、计价、折叠函数（零外部依赖）
  usecase/     → 用例编排：事务边界、权限校验、跨模块协作
  adapter/
    http/      → 路由、中间件、DTO 转换
    postgres/  → sqlc 静态 SQL、squirrel 动态筛选、扁平 DTO、迁移
    redis/     → 缓存与锁（R2 起）
  platform/    → 配置、日志、UoW、错误、指标、追踪
  di/          → wire 装配
```

依赖单向向下：`domain` 不得 import `adapter` / `platform`；`usecase` 只依赖 `domain` 与接口；`adapter` 实现接口。由 lint 规则强制，详见 `04`。

## 7. 本轮引入、但尚未 ADR 化的设计提案

以下属于**设计提案**，需评审通过后另立 ADR；本套文档按提案描述，但不得视为已接受决策：

| 编号 | 提案 | 影响 | 见 |
|---|---|---|---|
| DP-01 | 采用模块化单体，R1–R4 不拆微服务 | 部署、事务边界 | 本册第 4、6 节 |
| DP-02 | 报表三层读模型（实时 / 预聚合 / 流式导出） | 新增汇总表与 worker | `05` 第 8 节 |
| DP-03 | 事务内只写 Outbox，由 worker 派发领域事件 | 新增事件表与投递语义 | `05` 第 7 节 |
| DP-04 | 错误分类显式标注「可重试 / 不可重试」 | 全局错误码与客户端行为 | `03` 第 4 节 |
| DP-05 | 已支付单据不可变，更正走退款单 + 新单 | 状态机与审计 | `01` 第 5 节、`06` 第 2 节 |
| DP-06 | 契约冻结：OpenAPI + 响应快照测试 | CI 与前后端协作 | `03` 第 9 节 |
| DP-07 | R1 先用数据库实现幂等与锁，R2 再引入 Redis | 依赖引入节奏 | `05` 第 3、9 节 |

> **DP-01 与 ADR-0007 的关系**：「支持编排平台」只要求进程无状态、可水平扩缩，**不等于拆微服务**；模块化单体与单库事务不变。若评审决定拆微服务，DP-01 与 ADR-0007 第 3 节都要一起修订（见 8.2 NQ-01 / NQ-03）。

### 8.1 已确认决议（ADR-0004 / 0005 / 0006 / 0007，2026-11-15）

**OQ-01 至 OQ-08 已全部关闭，不再有开放问题。** [ADR-0004](../decisions/0004-scope-baseline.md) 冻结四项范围问题；[ADR-0005](../decisions/0005-no-shop-groups.md) 取消设计初版内置的门店组假设；[ADR-0006](../decisions/0006-user-shops-and-current-shop.md) 明确用户与门店的关系基数及当前门店切换协议；[ADR-0007](../decisions/0007-remaining-open-questions.md) 冻结最后五项（OQ-03 其余 / 04 / 05 / 07 / 08），其中 OQ-05 覆盖「先单机」默认假设、OQ-08 覆盖「审计日志不可删除」默认假设并修订 ADR-0004 第 3 节第 3 条。本文各分册按这四份 ADR 的口径描述。

| ADR-0006 | 初版未定义：用户与门店的关系基数、「当前门店」是什么 | **一个用户可拥有多间门店，可在页面切换**：从主体视角 1:N，关系实现仍是 `user_shops` 多对多（一店也可多人）；禁止 `users.shop_id` / `shops.owner_user_id`；当前门店是请求期上下文，不落表、不进 JWT、不作授权来源；单店请求必须显式带 `X-Shop-Id`；切换零写入、无服务端端点 | `01` §2/§6、`02` §2/§3/§8、`03` §3/§7、`04` §4、`05` §1/§5、`06` F-07 |
| OQ-03（其余） | 支付网关 / 短信 / 对象存储哪些进 R1？ | **R1 不接任何外部服务**：Outbox 订阅者全在进程内；`usecase/port/` 与 `adapter/gateway/` 只留接口位置，不放 SDK；接入时另立 ADR | `04` §1、`05` §7、`03` §8 |
| OQ-04 | `porch-console` 前端框架 | **确认决策权归属**：由前端仓独立决策，后端只保证 REST + OpenAPI、不做 BFF；**具体框架仍未选定**（见 8.2 NQ-14） | `03` §1、`04` §1、前端仓 README |
| OQ-05 | 部署形态？是否读写分离？ | **支持编排平台、暂不读写分离**：`api` / `worker` 无状态可水平扩缩；单主库读写，无只读副本；迁移独立一次性执行、定时任务数据库锁防重、连接池按副本数推导；本地 Compose 仅开发用 | `00` §3、`02` §6、`04` §3、`05` §7/§8/§10 |
| OQ-07 | 跨店会员消费的门店间差额如何结算？ | **不做自动清分**：只记录消费发生在哪家店；不引入往来账 / 结算单 / 清分任务；差额用按店分组的报表呈现，将来需要时另立 ADR | `01` §3、`06` F-03、`05` §8 |
| OQ-08 | 审计日志留存？ | **默认保留 30 天、可配置、定时删除**：`audit_logs` 属基础设施 / 运行期数据，不受「业务数据暂不归档」约束；业务请求仍只追加不可改删，唯一删除者是 worker 清理任务；不归档、不分区；超期查询返回明确语义而非空结果（**修订**初版「不可删除」假设） | `02` §2/§7、`04` §3、`05` §7/§11、`03` §8 |

> 「运行期清理 ≠ 业务归档」「离线提示 ≠ 离线收银」「文件导出 ≠ 打印」三组边界由 ADR-0004 明确；**「取消门店组 ≠ 取消跨店汇总」**由 ADR-0005 明确；**「一人多店 ≠ 一店一人」「当前门店 ≠ 授权来源」「页面切换 ≠ 跨店汇总」**由 ADR-0006 明确；**「审计日志定时删除 ≠ 业务数据归档」「运行期清理 ≠ 业务单据删除」「业务请求不可删审计 ≠ 清理任务不可删」「支持编排平台 ≠ 拆微服务」**由 ADR-0007 明确，评审时不得混用。

|---|---|---|---|
| NQ-01 | DP-01–07 七项设计提案是否逐项接受（尤其 **DP-01「模块化单体、不拆微服务」** 与「支持编排平台」需一起确认） | 设计冻结的前置；DP-01 若改，事务边界与部署约束全部重算 | 架构评审 / 用户 |
| NQ-02 | ADR-0006 的「1 对多」是**主体视角 1:N + `user_shops` 多对多**（当前口径），还是严格 1:N 的 `users.shop_id` 外键 | 直接决定授权表与 schema；若改需重做 ADR-0006 与切换协议 | 用户 |
| NQ-03 | 详细设计何时冻结、R1 首批端点范围与验收标准 | R1 开工的前置；契约冻结（DP-06）依赖它 | 用户 / 后端 |
| NQ-04 | 容量与告警阈值的具体数值（表体积、慢查询比例、库体积、连接池水位） | ADR-0004「暂不归档」要求容量可观测，但阈值原定 R1 压测后给 | 后端 / 运维 |

**B. 编排平台落地，ADR-0007 衍生（P0 / P1）**

| 编号 | 待确认问题 | 为什么必须先答 | 归属方 |
|---|---|---|---|
| NQ-05 | 具体编排平台：Kubernetes / Nomad / 云容器服务？清单由谁产出、是否 R0 就要交付 | 决定部署脚本、ConfigMap/Secret、探针与发布流水线形态（P1，不阻塞 R1 编码） | 用户 / 运维 |
| NQ-06 | 迁移执行方式：独立一次性 Job 还是发布流水线步骤；`/ready` 如何判定「迁移版本不符不接流量」 | 多副本下每个 Pod 各自跑迁移会破坏 schema（P0，上线前必答） | 后端 / 运维 |
| NQ-07 | 连接池预算数值：`api` / `worker` 副本数、每实例 `max_conns`、PG `max_connections` 运维预留 | 多副本 × 默认连接数会直接打满数据库连接（P0，压测前必答） | 后端 / 运维 |
| NQ-08 | worker 多副本定时任务的锁粒度、执行键命名、副本数上限与扩缩容行为 | 保证「同一任务任意副本数下只跑一次」（P1） | 后端 |
| NQ-09 | 配置与密钥注入方式、Ingress / TLS 终止位置、滚动发布与优雅停机时长 | 部署形态确定后才有唯一答案（P1） | 运维 |

**C. 审计日志 30 天保留，ADR-0007 衍生（P1）**

| 编号 | 待确认问题 | 为什么必须先答 | 归属方 |
|---|---|---|---|
| NQ-10 | `AUDIT_LOG_RETENTION_DAYS` 的取值规则：**30 天是默认值还是硬上限**、是否允许关闭清理（0 / 永不删除）、是否可按店覆盖、变更是否需重启 | 「只保留 30 天」与「支持配置」的组合口径；直接决定配置校验与合规风险 | 用户 / 后端 |
| NQ-11 | 清理窗口口径：按 UTC+8 自然日还是滚动 30×24h；任务频率、单批行数、`VACUUM` / 表膨胀策略 | 决定删除 SQL、索引与对在线请求的影响 | 后端 |
| NQ-12 | 超期查询的错误码与文案；窗口内是否单独提供审计导出端点 | 冻结接口契约（DP-06）前必须定，否则前端会把「超出保留期」当成空结果 | 前后端 |
| NQ-13 | 清理动作的可观测口径（指标名、告警阈值），以及是否需要在 `audit_logs` 之外留一条「已清理至某日期」的痕迹 | 不写回审计表可避免自我循环，但需有独立的运行记录 | 后端 / 运维 |

**D. 不阻塞 R1，但需登记（P2）**

| 编号 | 待确认问题 | 说明 | 归属方 |
|---|---|---|---|
| NQ-14 | `porch-console` 具体框架、API 客户端、状态管理、组件库、E2E | OQ-04 只确认了归属；选型由前端仓独立决定 | 前端 |
