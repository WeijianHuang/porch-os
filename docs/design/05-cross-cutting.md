# 前期系统架构详细设计 · 05 横切机制

> 上游：[00 总览](00-overview.md) 第 2 节（质量属性）、[03 接口设计](03-api-design.md)（错误码与幂等头）、[04 应用架构](04-application-architecture.md)（中间件链与 UoW）、[ADR-0004](../decisions/0004-scope-baseline.md)（范围基线）、[ADR-0005](../decisions/0005-no-shop-groups.md)（授权唯一来源）、[ADR-0006](../decisions/0006-user-shops-and-current-shop.md)（一人多店、当前门店不落库、缓存键含门店）、[ADR-0007](../decisions/0007-remaining-open-questions.md)（编排平台、暂不读写分离、审计日志保留 30 天定时删除）、[ADR-0008](../decisions/0008-design-freeze-and-nq-resolutions.md)（设计冻结、Docker 2+2、Go Job、审计与容量基线）。
> 本册定义「跨所有模块都成立的机制」。这些机制一旦漏一个，症状通常是**静默错数据**而不是报错，所以优先级高于便利性。

## 1. 认证与授权

| 项 | 规则 |
|---|---|
| 密码 | `x/crypto/bcrypt` 哈希，永不明文存储或记录到日志 |
| 访问令牌 | JWT 短时效（15 min），载荷只放主体 ID 与令牌版本，不放角色 / 门店清单 / 当前门店（ADR-0006） |
| 刷新令牌 | 服务端存哈希、可撤销、可轮换；不进 URL、不进 localStorage 的日志路径 |
| 权限来源 | 每次请求从 `user_roles` + `role_permissions` 实时推导 |
| 门店范围 | 每次请求从 `user_shops` 推导「可见门店集合」（一个用户可有 N 家店，一店也可有多个用户），注入 context 供用例层使用；**这是唯一来源**，不经过门店组 / 父子门店 / 标签分组（ADR-0005） |
| 当前门店 | 单店请求必须显式带 `X-Shop-Id` 并与可见集合求交；**不落库、不进 JWT、不作为授权来源、无服务端切换端点**；切换只是客户端换一个集合元素，不触发授权重算（ADR-0006） |
| 判定结果 | **不缓存**；授权变更后下一个请求即生效 |
| 跨店权限 | `report.cross_shop` 等显式权限点；请求里的门店列表仍与可见集合求交；**不存在按组授权**，门店集合也不是可持久化的业务对象 |

> JWT 里不放权限与门店清单，是因为它们会随授权变更过期；把清单写进令牌等于把「立即生效」变成「等令牌过期」。这与 ADR-0002 阻断项 ⑧ 是同一条约束。

## 2. 幂等

幂等不是中间件里的一行 `SETNX`，而是「业务写入 + 幂等记录 + 事件」三者的原子提交。

| 阶段 | 行为 |
|---|---|
| 请求到达 | `idempotency` 中间件校验 `Idempotency-Key` 存在，算 `request_hash`，建 `scope = user:<id>\|shop:<id>` |
| 查记录 | 无记录 → 插入 `in_progress`（与业务同事务）；有记录则比对 hash |
| 相同 hash + `completed` | 直接返回首次响应体与状态码，不执行用例 |
| 相同 hash + `in_progress` | `409 IDEMPOTENCY_IN_PROGRESS` + `Retry-After` |
| 不同 hash | `409 IDEMPOTENCY_CONFLICT`，绝不复用结果 |
| 用例成功 | 同一事务内把记录置 `completed` 并写入 `response_code` / `response_body` |
| 用例失败 | 事务回滚，幂等记录一并撤销，客户端可用同一 key 重试 |
| 清理 | worker 删除 `expires_at` 过期记录（默认保留 24 h） |

**并发窗口**：两个相同 key 的请求同时到达时，靠 `PRIMARY KEY (scope, key)` 让第二个插入冲突，转为「读取既有记录」路径；不依赖应用层互斥锁。R1 用数据库实现（DP-07），R2 若引入 Redis 只做加速，不改变原子提交语义。

## 3. ID 与单号生成

| 标识 | 生成方式 | 唯一性范围 |
|---|---|---|
| 内部主键 | `bigint GENERATED ALWAYS AS IDENTITY` | 表内 |
| `public_id` | PG 18 内置 `uuidv7()`（时间有序 UUID） | 全局唯一约束 |
| `order_no` 等人类可读单号 | 数据库序列 + 默认表达式 | `(shop_id, order_no)` **店内唯一** |
| 幂等键 | 客户端 UUID | `(scope, key)` |

禁止「应用层拼 `日期 + shopId + 计数器`」：并发下必然重复，且没有数据库兜底。单号格式变更走迁移，不能只改代码。若生产降级到 PG 17（ADR-0001 联动条款），`uuidv7()` 改由应用层生成后写入，其余不变。

## 4. 并发控制与事务隔离

| 场景 | 手段 |
|---|---|
| 同一单据并发修改 | 乐观锁 `version`，`UPDATE ... WHERE version = $n`，影响 0 行 → `VERSION_CONFLICT`（可重试） |
| 库存 / 余额扣减 | `SELECT ... FOR UPDATE` 行锁 + 条件更新 `WHERE balance >= $amount`，避免先读后写超卖 |
| 开班 | 部分唯一索引 `WHERE status = 'open'`，数据库层保证一店一个 |
| 死锁 / 序列化失败 | 映射为可重试错误，指数退避最多 3 次；重试必须复用同一幂等键 |
| 隔离级别 | 默认 `READ COMMITTED`；只有确需可重复读的报表快照才显式提升，且不得长事务 |
| 锁等待 | `lock_timeout = 3s`，避免一个慢事务拖住整个连接池 |

所有数据库调用接受 context；客户端断开 → context 取消 → 驱动取消查询 → **服务端计算必须随之终止**，不留后台空转。

### 4.1 在线强一致（ADR-0004：不做离线收银）

系统**不支持断网收银**：所有写操作必须在线同步完成，由单库事务保证「提交成功即已生效」。

| 明确不做 | 原因 |
|---|---|
| 本地队列 / 待同步单据 / 断网缓存 | 会把「写入是否生效」变成最终一致，破坏幂等与事务边界的唯一来源 |
| 恢复后补传、同步水位、设备时钟校正 | 需要设备级单号段与冲突解决，成本远超当前需求 |
| 离线状态下的提交放行 | 前端只提示网络不可用并保留草稿，恢复后由用户重新发起，复用同一 `Idempotency-Key` |

服务侧依赖不可用映射到 `502 DEPENDENCY_FAILURE`，客户端网络中断显示网络错误提示（错误码见 [03 第 4 节](03-api-design.md)），**不得**把离线期间的输入悄悄记为已生效单据。前端「离线提示」只表示网络不可用，不代表具备离线能力。

## 5. 缓存策略

**能被缓存的**（短 TTL + 写后失效）：目录项与分类、门店设置、权限点定义、字典数据。

**绝不能缓存的**：权限判定结果、可见门店集合（shop scope）、库存余额、会员余额、单据状态与金额、任何跨店聚合结果。

| 规则 | 说明 |
|---|---|
| 一律带 TTL | 禁止无过期缓存；进程内 `ristretto` 与 Redis 双层时，TTL 以较短者为准 |
| 写后失效 | 写操作提交成功后删除键，不用「等 TTL 自然过期」 |
| 键含门店维度 | 可缓存的门店级数据，键必须含 `shop_id`，避免跨店串数据 |
| 键含当前门店 | 前端派生查询与缓存以 `(user_id, current_shop_id, query_key)` 组织；切换门店时全部失效重取，并取消在途请求或丢弃旧门店响应（ADR-0006） |
| 缓存故障 | 降级为直查数据库，不能因为缓存不可用而拒绝服务 |
| 判定不缓存 | 权限与 shop scope 每次请求实时推导（第 1 节），缓存会破坏「立即生效」 |

## 6. 事务性事件（Outbox，DP-03）

事务内**不做外部 IO**，但需要「业务成功后发出通知」。解法是把事件写进同一张库、同一个事务：

```
用例事务：业务写入 + idempotency_keys + outbox_events  → COMMIT
worker：  批量领取未派发事件（FOR UPDATE SKIP LOCKED）
          → 投递到订阅者 / 触发汇总重算 → 标记 dispatched_at
          → 超过 attempts 上限 → 写 dead_letters 并告警
```

| 规则 | 说明 |
|---|---|
| 语义 | **至少一次投递**；订阅方必须按 `(event_type, aggregate_id, id)` 幂等 |
| 顺序 | 同一聚合内按 `id` 顺序；跨聚合不保证全局有序 |
| 载荷 | 只带 ID 与最小上下文，不带实体快照，避免载荷版本地狱 |
| 重试 | 指数退避；失败不阻塞业务事务 |
| 清理 | 已投递且超期的行定期删除（运行期清理，非业务归档，ADR-0004 / 0007）；**未投递的永不删除**；R1 的订阅者全部在进程内，不投递外部服务（ADR-0007） |
| 可观测 | 未派发积压量、最老事件年龄、死信数量都是必配指标 |

## 7. 后台任务与定时任务

| 项 | 规则 |
|---|---|
| 进程 | 只在 `cmd/worker`，`cmd/api` 请求处理器不启动长任务 |
| 调度 | `robfig/cron/v3` + 分布式锁（R1 用数据库 advisory lock，R2 可换 `redsync`）；**Docker 2+2 下每个执行键一把会话级 advisory lock，抢不到即跳过**；命名、Go 例子与「同一条连接加解锁」陷阱见 [07](07-deployment-and-operations.md) §4.2（ADR-0007 / 0008） |
| 幂等 | 每个任务有稳定的执行键；重复触发不产生重复汇总/重复扣减/重复删除 |
| 汇总重算 | 按 `(shop_id, business_date)` 幂等覆盖写 `daily_shop_summary`，不累加；`business_date` 按 UTC+8 口径 |
| 清理范围 | 只清理幂等键、已投递事件、导出临时文件、**审计日志超期记录**等运行期数据；**业务数据暂不归档、不设保留窗口**（ADR-0004 / 0007） |
| 审计清理 | 默认保留 30 天（`AUDIT_LOG_RETENTION_DAYS` 全局可配、启动时校验）；按 UTC+8 **自然日** cutoff 算截止点，每日 03:30、单批 5000 行、逐批提交、可重入、不建分区、不导出归档；运行痕迹落 `audit_log_cleanup_runs`，指标与告警见 [08](08-audit-retention.md) §5，**不写回 `audit_logs`**（ADR-0007 / 0008） |
| 失败 | 重试 + 死信 + 告警；不允许静默吞异常；清理失败不得悄悄缩短或延长保留窗口 |
| 停机 | 优雅停机：停止领取新任务，在途任务有超时上限 |

## 8. 报表三层读模型（DP-02）

不同时间跨度与数据量用不同读路径，避免「所有报表都实时扫大表」。

| 层 | 场景 | 读路径 | 约束 |
|---|---|---|---|
| **L1 实时** | 当前营业日（UTC+8 口径）、单店、简单聚合 | 主库直接查，条件聚合 / CTE | 5 s 超时；必须命中 `(shop_id, created_at)` 索引；禁止跨店大区间实时扫 |
| **L2 预聚合** | 日报、跨店对比、经营分析 | `daily_shop_summary` | worker 增量重算，记录 `recomputed_at` 供 UI 显示数据截至时间；业务日固定 UTC+8 |
| **L3 导出** | 大区间明细、Excel | 异步 `export_jobs` + keyset 游标 + `excelize.StreamWriter` 流式写出 | **禁止**先把结果集收集进 slice、禁止深 `OFFSET`、禁止把整个文件读进内存后再返回；内存占用与结果集大小无关 |

规则：

- L2 是**派生数据**：可从流水全量重算，定期对账，差异告警；不允许人工改汇总表。
- 跨店汇总就是 `GROUP BY shop_id` / `SUM(...) FILTER (WHERE ...)`，不需要第二层隔离维度，也不产生数据副本（ADR-0003）；**不按门店组聚合**，参与汇总的 `shop_ids` 已与可见集合求交（ADR-0005）。
- 复杂口径写在 `adapter/postgres/derived/*.sql`，受版本控制、可 diff、可 `EXPLAIN`；**不建数据库视图**。
- 导出任务失败要显式置 `failed` 并在响应里给出原因，不允许返回空文件或 `null`。
- L3 只产出 Excel / CSV 文件供下载，**不生成打印小票、不调用打印设备**（ADR-0004）；业务数据暂不归档，导出范围不受保留窗口裁剪。
- **暂不读写分离、不引入只读副本**（OQ-05 已由 [ADR-0007](../decisions/0007-remaining-open-questions.md) 关闭）：本期落地 Docker 2+2 多副本（ADR-0008 / [07](07-deployment-and-operations.md)），但所有读写走同一个主库，重报表靠 L2 预聚合与 L3 流式导出扛住；不引入复制延迟下的「刚结账查不到」。

## 9. 可观测性

| 类别 | 内容 |
|---|---|
| 结构化日志 | JSON，必带 `request_id`、`user_id`、`shop_id`（可空）、`route`、`status`、`duration_ms`、`error_code`；手机号等 PII 掩码；不记密码、令牌、请求体全文 |
| 指标 | 请求 QPS / 延迟分位 / 错误码分布、DB 连接池使用率与等待时长、慢查询数、Outbox 积压与最老事件年龄、死信数、导出任务时长与内存、缓存命中率、**表与索引体积 / 库体积 / 大表 `Seq Scan` 比例**（暂不归档，容量必须可观测，ADR-0004）、**`porch_audit_cleanup_*` 系列指标、`porch_audit_retention_days`、`porch_audit_earliest_queryable_timestamp_seconds`、清理运行记录与 7 条告警规则**（ADR-0007 / 0008，见 [08](08-audit-retention.md) §5） |
| 追踪 | OpenTelemetry，span 覆盖 HTTP → 用例 → SQL；采样率可配，错误请求强制采样 |
| 告警 | 5xx 比例、慢查询、Outbox 积压、连接池打满、跨店权限拒绝突增、导出失败率 |
| 健康检查 | `/health`（进程存活）、`/ready`（数据库连通 + 迁移版本符合预期） |

## 10. 超时、取消与连接池基线

| 配置 | 值 | 理由 |
|---|---|---|
| HTTP 普通 / 报表 | 5 s / 30 s | context 一路传到 SQL，客户端断开即终止计算 |
| `statement_timeout` | 5 s（报表会话 30 s） | 防止单条慢 SQL 占死连接 |
| `idle_in_transaction_session_timeout` | 10 s | 防止事务开着不提交 |
| `lock_timeout` | 3 s | 快速失败优于排队 |
| `max_conns` | **`api` 20 / `worker` 10 / `job` 5**（2+2 合计 80 ≤ 100） | **禁止使用驱动默认值**；`api` 与 `worker` 分开配；按「副本数 × 每实例上限 + 运维预留 ≤ PG `max_connections`」推导；预算表、压测基线与扩副本规则见 [07](07-deployment-and-operations.md) §4（ADR-0008） |
| 导出 | 无请求级超时（异步任务），但单批次有超时与重试 | 长任务不占 HTTP 连接 |

## 11. 安全基线

- 全站 HTTPS；CORS 显式来源白名单，生产禁用通配符；统一安全响应头。
- 输入在边界校验（validator），排序字段走白名单，动态 SQL 只用参数绑定。
- 日志与错误信息不含堆栈、SQL、密钥、PII；数据库原始错误不返回客户端。
- 审计日志 `audit_logs` 记录「谁、在哪个店、做了什么、什么结果」；**对业务请求只追加、不可更新删除**，唯一允许删除的是 worker 定时清理任务（默认 30 天、取值 `1..3650`、UTC+8 自然日窗口、分批可重入、有运行痕迹与告警，ADR-0007 / 0008，见 [08](08-audit-retention.md)）。这不是业务数据归档，也不允许把清理范围扩展到单据 / 流水。
- 依赖用 `govulncheck` 扫描；镜像多阶段构建到 `distroless/static`，非 root 运行。
- 限流按「主体 + 门店」，防刷与防越权枚举；越权拒绝统一 `403`，不区分门店是否存在。
