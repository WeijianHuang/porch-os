# 前期系统架构详细设计 · 09 跨店差额与清分边界

> 状态：**已冻结**（[ADR-0008](../decisions/0008-design-freeze-and-nq-resolutions.md)，2026-11-15）。
> 上游：[ADR-0003](../decisions/0003-shop-level-isolation.md)（一条业务记录只属于一个 `shop_id`）、[ADR-0005](../decisions/0005-no-shop-groups.md)（跨店按显式门店集合）、[ADR-0007](../decisions/0007-remaining-open-questions.md) 第 4 节（不做自动清分）、[ADR-0008](../decisions/0008-design-freeze-and-nq-resolutions.md)（NQ-16：需要详细说明）、[06 关键流程](06-key-flows.md) F-03/F-05。
> 本册是对 NQ-16 的展开说明：**维持「不做跨店自动清分」不变**，把差额的来源、数据记录方式、按店分组的呈现口径、适用边界与未来启用条件讲清楚。它不新增任何表、端点或任务。

## 1. 一句话结论

**跨店差额只作为「按店分组的报表事实」呈现，不生成结算单、不产生门店间债权、不自动改写任何账务数据。**

ADR-0007 第 4 节的决策不变。本轮答复是「需要详细说明」，因此这里补充口径而不是启用清分；若将来要**启用**自动清分，属范围变更，须另立 ADR 并推翻 ADR-0007 第 4 节，不能靠在报表里加一列「应结算金额」渐进引入。

## 2. 差额从哪里来

跨店共享实体（会员档案、商品目录）是**全局唯一**的，但由它们产生的一切业务副作用都带 `shop_id`（[00 第 5 节](00-overview.md) 三分法）。共享与按店归属之间的错位，就是差额的来源：

| # | 场景 | 发生了什么 | 数据表现 |
|---|---|---|---|
| 1 | 会员在 A 店建档 / 充值，在 B 店消费 | 钱进 A 店的账，商品或服务由 B 店提供 | `balance_ledger` 中 A 店一条贷记、B 店一条借记 |
| 2 | 跨店核销（显式业务动作，[06](06-key-flows.md) F-03） | 用 A 店账上的余额结 B 店的单 | 两店各写一条流水，用同一个 `transfer_ref` 关联；**不修改会员档案归属** |
| 3 | 跨店库存调拨（显式动作） | 货从 A 店移到 B 店 | `stock_transfers` + 两店各一条 `stock_movements`；**是库存动作，不是财务清分** |
| 4 | 跨店报表汇总（[05](05-cross-cutting.md) §8） | 把多家店放在一张表里对比 | 只读 `GROUP BY shop_id`，不写任何数据 |

**共同点**：每一条流水都只有一个 `shop_id`；系统从头到尾没有回答过「A 店该还给 B 店多少钱」这个问题，只是如实记录「钱在哪家店进、在哪家店出」。

> 「一条业务记录只属于一个 `shop_id`」是 ADR-0003 的硬约束。差额本身**不是一条业务记录**，它是把多条按店记录放在一起比较后得到的**只读派生结果**，因此不落表、不生成 ID、不成为授权或归属维度。

## 3. 数据怎么记

### 3.1 写入侧（唯一口径）

| 规则 | 说明 |
|---|---|
| 归属 | 每条 `balance_ledger` / `stock_movements` / `orders` / `payments` 都带 `shop_id`，复合索引以它为前导 |
| 跨店关联 | 跨店核销 / 调拨用 `transfer_ref` 把两店的流水对上；**它只是关联键，不是债权凭证** |
| 会员档案 | `members` 全局唯一、不带 `shop_id`；余额按店存 `member_balances (shop_id, member_id)` |
| 禁止 | 不建 `inter_shop_receivables` / `internal_settlements` / 结算单 / 清分任务表；不给 `balance_ledger` 加 `owed_by_shop_id`；不把 A 店的流水复制一份到 B 店 |

### 3.2 示例（合成数据，仅用于说明口径）

| 步骤 | 门店 | 动作 | 流水 |
|---|---|---|---|
| 1 | A 店 | 会员 M 充值 | A 店 `+100.00` |
| 2 | B 店 | 会员 M 消费 | B 店 `-60.00`（跨店核销，`transfer_ref = T-001`） |
| 3 | 报表 | 按店分组 | A 店净额 `+100.00`，B 店净额 `-60.00` |

**系统里存在的**：两条带 `shop_id` 的流水、一个 `transfer_ref`、两张按店余额。
**系统里不存在的**：任何「A 店欠 B 店 60.00」的记录、任何结算单、任何自动转账。要抹平这 60.00，由经营者在系统外按自己的经营规则处理；系统提供的是可核对的数据，不是替他做决定。

### 3.3 读取侧（报表口径示意）

跨店报表走 [05 §8](05-cross-cutting.md) 的 L2 预聚合 / 条件聚合，复杂 SQL 放 `adapter/postgres/derived/*.sql`，受版本控制、可 diff、可 `EXPLAIN`；**不建数据库视图**（ADR-0002 阻断项 ③）。下列 SQL 只表达聚合方式，字段命名以 [02](02-database-design.md) 最终 DDL 为准：

```sql
-- 各店区间净额：条件是「可见门店集合 ∩ 显式 shop_ids」，与当前门店切换无关（ADR-0005/0006）
SELECT shop_id,
       SUM(amount) FILTER (WHERE direction = 'credit') AS inflow,
       SUM(amount) FILTER (WHERE direction = 'debit')  AS outflow,
       SUM(amount) AS net_amount
FROM balance_ledger
WHERE shop_id = ANY($1::bigint[])          -- 已与可见集合求交
  AND occurred_at >= $2 AND occurred_at < $3  -- 半开区间，UTC+8 业务日
GROUP BY shop_id
ORDER BY shop_id;
```

```sql
-- 会员跨店收支对照：把「钱在哪家店进、在哪家店出」摊开给经营者看
SELECT l.shop_id,
       m.public_id AS member_id,
       SUM(l.amount) FILTER (WHERE l.direction = 'credit') AS credit,
       SUM(l.amount) FILTER (WHERE l.direction = 'debit')  AS debit,
       SUM(l.amount) AS net_amount,
       COUNT(*) FILTER (WHERE l.transfer_ref IS NOT NULL)  AS cross_shop_entries
FROM balance_ledger l
JOIN members m ON m.id = l.member_id
WHERE l.shop_id = ANY($1::bigint[])
  AND l.occurred_at >= $2 AND l.occurred_at < $3
GROUP BY l.shop_id, m.public_id
ORDER BY m.public_id, l.shop_id;
```

两个查询都只读、都不产生持久化对象；导出时复用统一导出任务与流式写出（[05](05-cross-cutting.md) §8）。权限仍需 `report.cross_shop`，`shop_ids` 先与可见集合求交，越权项直接拒绝而非静默忽略（[03](03-api-design.md) §3）。

## 4. 为什么不做自动清分

| 一旦自动清分，就必须回答 | 与现有决策的冲突 |
|---|---|
| 哪家店欠哪家店、按什么规则判定方向 | 需要给一条流水附加第二个门店归属，直接违反 ADR-0003「一条业务记录只属于一个 `shop_id`」 |
| 结算周期、周期切点、跨周期订单归哪期 | 会引入第二套时间口径；ADR-0004 只定义 UTC+8 业务日，没有结算期概念 |
| 历史数据从哪天开始清分、已发生差额是否追溯 | 业务数据暂不归档、全量保留（ADR-0004），「开账日」会凭空切出一段不可比的历史 |
| 差错、冲正、退款、审批流 | 需要新状态机、新幂等边界与新的审计口径，而 R1 尚无需求 |
| 报表同时回答「谁卖了」与「谁该收钱」 | 现有报表按 `shop_id` 分组只回答前者；两套口径混在一张表里会让日报对不上账 |
| 加盟 / 独立核算主体之间的债权 | README 边界已明确**不做加盟 / 连锁总部体系**，本项目的所有门店同属一个经营主体 |

换句话说：自动清分不是「在报表里多算一列」，而是要引入一整套**第二归属维度 + 结算状态机 + 历史口径**。这与本项目的隔离模型、范围基线和业务定位同时冲突，代价远高于它当前能带来的价值。

## 5. 「按店分组呈现差额」是否满足经营需要

按 README 的定位（一个经营主体、多间门店）逐项判断：

| 经营需要 | 是否满足 | 系统提供的手段 |
|---|---|---|
| 知道钱在哪家店收、在哪家店花 | ✅ 满足 | 按店流水、按店净额、会员跨店收支对照 |
| 能对账、能查出某笔跨店核销的两条流水 | ✅ 满足 | `transfer_ref` 关联 + 全量保留（暂不归档，可一直追溯） |
| 看多店趋势、对比各店经营情况 | ✅ 满足 | `scope=all` + 显式 `shop_ids` 的 `GROUP BY shop_id` 报表 |
| 数据不被悄悄改写、每笔都有据可查 | ✅ 满足 | 差额只是只读派生结果，不写回任何账务表 |
| 门店之间自动结转、生成结算单 | ❌ **不满足（有意）** | 由经营者在系统外按自己的规则处理 |
| 门店是独立核算 / 加盟主体、需要分账 | ❌ **不在范围** | 属 README 明确排除的加盟 / 连锁总部体系 |

**判断口径**：只要多家店同属一个经营主体、经营者要的是「看得清」而不是「自动分钱」，按店分组就够用。一旦出现「各店独立核算」「加盟分账」「定期结算」，那就是另一个业务形态，须走新 ADR，而不是给现有报表加字段。

## 6. 边界澄清（评审时不得混用）

- **跨店核销 ≠ 清分**：前者是一次显式业务动作，写两条带 `shop_id` 的流水；后者会改写门店间债权债务，系统不做。
- **跨店调拨 ≠ 清分**：前者是库存数量在两店间的移动，不产生任何财务结算记录。
- **报表分组 ≠ 账务转移**：`GROUP BY shop_id` 是只读计算，不生成单据、不落表、不改变归属。
- **暂不归档 ≠ 差额凭证**：全量保留让差额**可追溯**，但系统不提供「可举证的结算凭证」；如需法定凭证，属合规范围扩展。
- **不做清分 ≠ 不做跨店汇总**（承接 ADR-0005 的边界）：跨店汇总 / 对比 / 导出能力完整保留，只是不自动改写账务。
- **可见门店集合 ≠ 结算范围**：`shop_ids` 是查询范围与授权求交的结果，不是结算对象集合。

## 7. 未来启用清分的触发条件与必须定义项

**触发条件**：出现真实的独立核算 / 加盟分账需求，且经营者要求系统自动生成结算结果（而不是人工在系统外处理）。

启用前须另立 ADR，并**至少**定义以下七项；任何一项缺失都不得开工：

1. 结算周期（日 / 月）、切点时区（仍为 UTC+8，但需定义周期边界与跨期单据归属）；
2. 债权方向规则：什么动作产生「谁欠谁」，与 `shop_id` 单层归属如何共存（必然要复审 ADR-0003 第 6 条）；
3. 历史数据口径：开账日、历史差额是否追溯、如何与「业务数据全量保留」共存；
4. 差错处理：退款、冲正、跨期调整、审批与撤销；
5. 幂等与并发：结算单生成不能重复，批量结算不能与在线收银互相阻塞；
6. 报表口径：同时呈现「谁卖了」与「谁该收钱」，且日报能对上账；
7. 与外部财务 / 开票系统的边界（本项目不替代财务软件）。

同时必须复审 ADR-0007 第 4 节、ADR-0003 第 6 条与 [00 第 5 节](00-overview.md) 的数据归属三分法，并同步 `design/01`–`06` 与 README 边界。**该类变更不是 NQ 清单的重新打开**，而是新 ADR + 设计变更。

## 8. 测试与验收

| 场景 | 断言 |
|---|---|
| 跨店核销 | 两店各一条流水、`transfer_ref` 相同、`shop_id` 各自正确；会员档案 `shop_id` 不存在；无结算单产生 |
| 归属约束 | schema 中不存在 `inter_shop_*` / `internal_settlement*` 表，流水上无第二个门店归属列 |
| 报表分组 | `scope=all` + `shop_ids` 与可见集合求交后按 `shop_id` 分组，结果与按店逐条相加一致；切换当前门店不改变跨店结果 |
| 只读性 | 跑跨店报表 / 导出前后，所有业务表的行数与金额不变 |
| 追溯 | 业务数据全量保留，任意历史区间的跨店差额都能重新算出来，且与当时报表一致 |
| 范围排除 | 端点清单中不存在结算 / 清分 / 往来账相关路径（[03](03-api-design.md) §8） |
